# Игровой API SDK 1.0

SDK 1.0.0 предоставляет эти интерфейсы для C++ и Rust через ABI 1, API 1.
C ABI использует копии JSON в UTF-8 и буферы вызывающей стороны;
Rust возвращает `Option<String>`, а C++ заполняет `std::string` и возвращает `bool`.
Указатели движка, объекты STL и Rust не пересекают границу ABI. Если снимок
недоступен, чтение возвращает zero/None/false. Неизвестные поля следует игнорировать.

## События

События и поля снимков, получаемые из сообщений, требуют обработчика,
зарегистрированного через обёрнутую таблицу движка штатного клиента или client_mini.
Сообщения, зарегистрированные только через другие таблицы, не наблюдаются.
Для `HealthInfo` и `Account` резервные обработчики не регистрируются: обновления
из этих сообщений тоже требуют наблюдаемого обработчика. Снимки данных
движка, уведомления о соединении, входе/выходе игроков, голосе и кварах
не зависят от этого наблюдателя.

Вызывайте `subscribe_event("player.health", true)` при загрузке или в последующем
обработчике. Для отписки передайте `false`. Реализуйте `Plugin::event(name, json)`
в C++ или `fn event(&mut self, host: &Host<'_>, name: &str, json: &str) -> Result`
в Rust. Подписки принадлежат отдельному плагину, сопоставляются по точному имени,
идемпотентны и не воспроизводят прошлые события. Неизвестные имена вызывают отказ.
Обработчики выполняются в игровом потоке поочерёдно между плагинами в проходе
доставки с ограниченным бюджетом, перед проходом кадровых обработчиков. Очередь
каждого владельца сохраняет порядок, но порядок между владельцами не совпадает
с порядком загрузки. При достижении лимита события ждут следующих кадров.
События, созданные обработчиком, ждут следующего кадра; разбор сообщений движка
и функции записи кваров никогда не вызывают обработчики плагинов напрямую.
См. [лимиты доставки](EXTENSIONS.ru.md#события-задачи-и-хранилище).

Все события ниже доступны без разрешений, кроме `chat.message` (`chat.read`)
и `cvar.changed` (`cvars.read`). На последнее подписывайтесь через `watch_cvar`,
фильтрующий по имени переменной, а не через `subscribe_event`. Разрешение проверяется
при подписке и при доставке. Ошибка обработчика отключает плагин и плагины,
для которых он является обязательной зависимостью. События позволяют наблюдать
состояние, но не отменять поведение движка.

События из сообщений содержат клиентское `time`. Конец раунда распознаётся
по системным токенам CS для победы, ничьей, бомбы, заложников и VIP; произвольный
текст сервера не становится событием, доступным без разрешения. Чат включает
полученные SayText и TextMsg с HUD_PRINTTALK, сохраняя исходные токены формата
и аргументы. Ввод текста в чат и голосовой звук не перехватываются.
Форматы пользовательских сообщений не определяются автоматически.

Наблюдатель игнорирует некорректные и обрезанные сообщения, не меняя снимки.
Доставка событий не гарантирована: у каждого плагина очередь максимум
на 2 048 событий и 1 МиБ JSON. Дополнительные события отбрасываются с уведомлением
через `sdk.overflow`; лимиты обработки и диагностика описаны в
[интерфейсах расширений](EXTENSIONS.ru.md). Данные публичного сообщения занимают
не более 64 КиБ. Изменение квара может содержать два значения до 65 535 байт каждое.
События — уведомления, а не надёжный журнал для воспроизведения; для текущего
состояния используйте снимки.

### Необязательные сообщения в формате ReGameDLL

Установка ReGameDLL или определение его версии не требуются. Стандартные сообщения
разбираются независимо от дополнительных полей. Дополнительные поля разбираются
только при получении; другой серверный аддон может отправлять тот же документированный
формат. Отсутствующие поля означают неизвестные значения, а не ноль или false.
Не предполагайте, что все сообщения о смерти содержат одинаковые расширения.

После стандартной строки оружия в `DeathMsg` может идти беззнаковое 32-битное
`death_flags`, определяющее наличие полей в следующем порядке передачи:

| Бит | Поле | Значение |
| --- | --- | --- |
| `0x001` | `death_position` | Три координаты смерти жертвы, не место попадания пули и не текущая позиция игрока |
| `0x002` | `assister` | Индекс игрока 1–32 или 0 при явно указанном отсутствии помощника |
| `0x004` | `kill_flags`, `kill_details` | Беззнаковые 32-битные флаги особенностей убийства и расшифрованные логические значения |

`kill_details` содержит `headshot` (0x001), `killer_blind` (0x002), `noscope`
(0x004), `penetrated` (0x008), `through_smoke` (0x010), `assisted_flash` (0x020),
`domination_began` (0x040), `domination` (0x080), `revenge` (0x100) и `in_air`
(0x200). `headshot` верхнего уровня соответствует стандартному байту сообщения.
В исходных флагах сохраняются неизвестные биты; неизвестные данные в конце
не интерпретируются. Если заявленное расширение обрезано, всё сообщение считается
некорректным, без частичного обновления снимков. Стандартные сообщения не содержат
этих дополнительных полей. Явно переданные нулевые флаги сохраняются.

`HealthInfo` и `Account` содержат индекс игрока, за которым идут знаковые 32-битные
здоровье или деньги. Значения сохраняются без сужения разрядности, включая ноль
и числа больше 255. Серверный маркер скрытого значения -1 превращается в null
и заменяет любое кешированное значение. Другие отрицательные значения сохраняются
как знаковые данные сервера. Эти обновления не перезаписывают локальные здоровье
или деньги HUD и не означают событие урона.
`ScoreAttrib` сохраняет все биты атрибутов; бит 0x008 сообщает о наборе сапёра.
Сброшенный бит не позволяет отличить отсутствие набора, скрытый набор и сервер
без поддержки, поэтому `has_defuser` становится null, а не false. Начало раунда
очищает кеш сообщённых здоровья, денег, набора сапёра и исходных флагов атрибутов;
повторное использование слота игрока, инициализация HUD и смена карты или сервера
также сбрасывают эти значения.

ReGameDLL управляет этими расширениями через `mp_deathmsg_flags`,
`mp_scoreboard_showhealth`, `mp_scoreboard_showmoney` и `mp_scoreboard_showdefkit`.
Клиент не запрашивает и не меняет эти настройки. См. исходные
[отправку сообщений](https://github.com/rehlds/ReGameDLL_CS/blob/master/regamedll/dlls/multiplay_gamerules.cpp),
[обновления игроков](https://github.com/rehlds/ReGameDLL_CS/blob/master/regamedll/dlls/player.cpp)
и [конфигурацию](https://github.com/rehlds/ReGameDLL_CS#configuration-cvars).

Обычное `Damage` содержит величины урона размером в байт, флаги урона,
отфильтрованные для HUD, и позицию источника урона. Оно не определяет нападавшего,
оружие, часть тела или нанесённый другим игрокам урон; несколько попаданий могут
объединяться в одно обновление.

## Полные данные клиента

`game_data(section, index)` предоставляет копии состояния, видимого клиенту.
Он **не** даёт доступа к данным только на сервере, скрытым противникам,
закрытым инвентарям или достоверным здоровью и скорости других игроков,
которые сервер не передал. Сетевые объекты и объекты предсказания сохраняют имена
и значения полей HLSDK; пользовательские поля модификаций передаются без обработки.

| Раздел | Индекс | Результат |
| --- | --- | --- |
| `player` | Игнорируется | Поля локального типизированного снимка, полный `clientdata_t` в `client`, полный предсказанный `entity_state_t` в `entity`, копии полей движения в `movement` (гравитация, трение, hull, состояния земли/воды/приседания, таймеры, векторы, текстура и пользовательские поля мода), `shots_fired` и кешированное состояние `hud` |
| `entity` | Индекс сущности | Все поля `entity_state_t`, `render_origin`, `render_angles`, `model_name`, `is_player`, `known_health` |
| `entities` | Игнорируется | Массив индексов доступных сейчас сущностей; каждую запрашивайте через `entity` |
| `weapon` | ID оружия 1–63 | `id`, `owned`, `definition`, полный `weapon_data_t` в `prediction`, `reserve`, `reserve2` |
| `weapons` | Игнорируется | Массив всех известных определений и предсказаний оружия |
| `ammo` | Игнорируется | Массив из 32 значений запаса боеприпасов; неизвестные элементы — null |
| `scoreboard` | 0 для всех или индекс игрока | Заполненные строки: `index`, `user_id`, `steam_id` (строка), `name`, `model`, `ping`, `packet_loss`, `local`, `spectator`, `frags`, `deaths`, `class`, `team_id`, `team`, `dead`, `has_c4`, `vip`, `attribute_flags`, `has_defuser`, `location`, `reported_health`, `reported_money`, `radar_position` |
| `match` | Игнорируется | Клиентские `time`, `map`, `paused`, `intermission`, `view_entity`, `game_type`, `round_seconds_remaining` и кешированное состояние сообщений |
| `connection` | Игнорируется | `state`, `connected`, `in_game`, `address`, `map`, `max_clients`, `hostname`, `demo_playback`, `demo_recording`, `latency`, `packet_loss`, `connection_time`, а при подключении также `remote_address` |

Данные подключения доступны всегда, когда подключён клиентский мост, в том числе
в меню. Имена состояний: `disconnected`, `connecting`, `connected`, `active`,
`uninitialized`, `dedicated` и `unknown`. API не включает пароли и исходные словари
userinfo/serverinfo. Разрешения на подключение или квары не требуются.

Остальным разделам нужны активная игра и корректное предсказание. Перечисление
сущностей включает только текущий сетевой кадр. `known_health` достоверно только
для локального игрока; исходные поля удалённой сущности не подтверждают известное
здоровье. Поля таблицы счёта, определения и запасы оружия могут быть null
до получения данных. Слоты игроков сбрасываются при уходе или повторном использовании;
смена карты или сервера очищает кеш. Определения оружия сохраняются при инициализации
HUD, поскольку процедура подключения может прислать их раньше. Чтение возвращает
не более 1 МиБ; короткий C-буфер очищается, возвращается нужный размер с NUL.
Считывайте размер и содержимое в одном игровом потоке.

Кеш состояния HUD и матча использует имя события как ключ, например
`player.money.money`, `player.armor.armor`, `round.time.seconds` или
`bomb.dropped.planted`. Отдельные словари — `team_scores`, `status_icons`,
`hostages`, `StatusValue` и `StatusText`. Это последние полученные значения,
не выдуманные значения по умолчанию и не полная история событий. Чат не включается.
Сброс HUD, новый раунд, подбор или сброс бомбы и сброс карты очищают соответствующий кеш.

Ограничения снимков: `match.team_scores` хранит до 32 имён, `match.status_icons` —
до 64 активных значков. Имена длиннее 64 байт UTF-8 и новые записи сверх лимита
не попадают в снимки, но их события доставляются. При заполнении лимита
существующие записи можно обновлять. Отключение значка удаляет его и освобождает
место. Сброс HUD очищает значки; инициализация HUD и сброс карты очищают оба словаря.

## Действия движка

`chat_print(text)` требует `chat.print` и выводит одну строку в локальном чате HUD.
Он не вызывает `say`/`say_team`, не отправляет сетевой трафик, не уведомляет
подписчиков чата и не дублирует текст в консоль. Если нужны оба вида вывода,
отдельно вызовите `console_print`, не требующий разрешения. Текст занимает
1–190 байт UTF-8, включая необязательные цветовые байты чата: `\x01` (по умолчанию),
`\x03` (командный) и `\x04` (зелёный). Другие управляющие символы и переводы строк
запрещены. Клиент должен находиться в активной игре; смерть не мешает локальному
выводу. `chat.send` и `chat.read` не предоставляют `chat.print`, и наоборот.

`create_cvar("counter", "0", true)` требует `cvars.create`, вызывается при загрузке
и регистрирует `nc.<plugin-id>.counter`. Локальные ID состоят из 1–48 строчных
ASCII-букв, цифр, подчёркиваний или дефисов; не более 32 кваров на плагин.
Начальные значения — до 4 096 байт. Доступен только флаг archive. Команды
и существующие квары нельзя заменять. Регистрация происходит после успешной
загрузки или подключения клиентского моста; ошибка регистрации блокирует или
отключает плагин. Квары существуют до завершения работы движка и не удаляются
при ошибке обработчика.

Чтение, запись и наблюдение за кварами принимают имена до 160 байт, включая полное
пространство имён `nc.<plugin-id>.<local-name>` (до 148 байт).

Создание переменной не разрешает её чтение, наблюдение или запись. `read_cvar`
и `watch_cvar(name, enabled)` требуют `cvars.read`, `write_cvar` — `cvars.write`.
Наблюдение сопоставляет точное имя без учёта регистра, допускает до 64 подписок
на плагин и может регистрироваться до создания квара. Событие начального значения
не генерируется. События отражают фактические изменения через функцию записи движка,
в том числе из консоли и конфигурации; одинаковые значения и отклонённые изменения
не создают событий. Прямую запись в память из нативного кода нельзя надёжно отследить.

`send_chat(text, team)` требует `chat.send` и действующего подключения без
воспроизведения демо. Текст — до 190 байт UTF-8; пустые строки, управляющие символы,
кавычки, обратные слеши и точки с запятой запрещены для предотвращения внедрения
команд. `team=true` выбирает командный чат. Получение независимо требует `chat.read`.
Ограничения серверного чата продолжают действовать.

`connect(host, port)` требует `connection.connect`, `disconnect()` —
`connection.disconnect`. Подключение может заменить текущее. Host — IPv4-адрес
или ASCII-имя DNS (до 253 байт), порт — 1–65535. URL, порт внутри адреса,
пароли, произвольные команды и синтаксис IPv6 не принимаются. В C++ порт
по умолчанию — 27015, Rust принимает `u16`. Команды передаются движку; успех
означает принятие к выполнению, а не установленное подключение. Для определения
результата наблюдайте за состоянием подключения.

## Постоянное хранилище каждого плагина

`store_set(key, json)` принимает любое корректное значение JSON: строку, массив,
объект, логическое значение, число или null. `store_get(key)` возвращает его
сериализованный JSON; отсутствующий ключ даёт None/false/zero, что отличается
от сохранённого JSON `null`. `store_delete(key)` идемпотентен. `store_keys()`
возвращает отсортированный JSON-массив. Ключи состоят из 1–96 строчных ASCII-букв,
цифр, точек, подчёркиваний или дефисов.

Каждому стабильному ID плагина соответствует `plugins/data/plugin-<id>.json`.
Ни один вызов API не принимает ID другого владельца или путь файловой системы.
Данные сохраняются при перезапуске игры, отключении и обновлении DLL с тем же ID.
«Отмена» в настройках не откатывает запись в хранилище. Это изоляция пространства
имён SDK, а не песочница ОС для нативных DLL.

Ограничения: 64 КиБ входного JSON на значение, 1 024 ключа, 1 МиБ сериализованного
хранилища и 16 уровней вложенных контейнеров JSON, включая объект хранилища.
При записи данные сбрасываются во временный файл, который атомарно заменяет старый;
при ошибке значения в памяти и на диске не меняются. Повреждение хранилища
приводит к отказу вызовов без скрытой перезаписи файла. Каталог игры должен быть
доступен для записи. Эти API синхронны и работают в игровом потоке; объединяйте
изменения и избегайте сохранения каждый кадр. Для атомарных транзакций с несколькими
ключами [интерфейс хранилища](EXTENSIONS.ru.md#события-задачи-и-хранилище)
предоставляет фоновые записи в то же хранилище плагина. API базы данных, общего
хранилища и произвольных файлов не предусмотрены.
