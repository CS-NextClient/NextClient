# Диагностика рендера моделей

[Английская версия](renderer-diagnostics.md) · [Устройство рендера](renderer-architecture.ru.md) | [Сценарии проверки](testing/studio-rendering.ru.md)

Команды выполняются вручную на загруженной карте в установленной игре. Перед проверкой новой сборки подготовьте и установите согласованный комплект модулей и ресурсов по [процедуре установки](testing/installation-and-factory.ru.md).

## Выбор пути отрисовки

```text
r_studio_shader 1
r_studio_materials 1
r_studio_queue 1
r_studio_info
```

Первая команда включает шейдерную отправку при наличии контекста OpenGL 3.3 с профилем совместимости. Вторая включает материалы. Обе настройки по умолчанию равны `1`. Значение `r_studio_materials 0` сохраняет GPU-скиннинг и отключает авторские материалы. Значение `r_studio_shader 0` выбирает отправку геометрии через движок.

`r_studio_queue` по умолчанию равен `1`. Перед отправкой последовательных подходящих пакетов в непрозрачном или прозрачном обходе Studio-моделей GL-состояние сохраняется один раз. После отправки всей серии оно восстанавливается. Значение `0` сохраняет шейдерный рендер с немедленной отправкой каждого пакета. Этот режим нужен для сравнения расходов очереди и для сторонних Studio-колбэков, которые вызывают OpenGL напрямую и не отправляют накопленную очередь перед рисованием. Remap-скины всегда отправляются сразу.

`r_studio_info` выводит последнюю захваченную studio-модель, размеры преобразованной геометрии, счетчики перехваченных вызовов и результат последней попытки шейдерной отрисовки. Один перехваченный вызов `StudioDrawPoints` считается одной отправкой; обычно он относится к одной части тела.

В пределах одной серии отправки рендер кеширует включение, коэффициенты и уравнения смешивания, проверку/запись/функцию/диапазон глубины, отсечение граней, alpha test и привязку базовой текстуры на unit 0. Значения пакета и переопределения masked/additive-мешей обновляют один кеш. Каждая серия начинается с неизвестных значений кеша. Восстановление состояния вызывающего кода остается безусловным; обычная отправка сохраняет привязку программы, uniforms, матрицы и загрузку костей каждого пакета. Подходящий rigid-батч применяет общее состояние один раз; см. [rigid-отправку](testing/studio-rigid-instancing.ru.md).

Команда также выводит число пакетов, максимальную длину серии, привязки studio-программ и отправки непустой очереди по причинам: brush, fallback, client, stage_end, capacity, resource, immediate и remap. Число перехваченных вызовов и вызовов, принятых шейдерным путем, накапливается за время работы модуля. Статистика очереди начинается с последнего непрозрачного обхода и включает последующий прозрачный обход и немедленные отправки до следующего непрозрачного обхода. Привязки не включают восстановление программы вызывающего кода и постороннюю работу с шейдерами. При обычной отправке каждый пакет сохраняет первую привязку программы для совместимости с драйверами, а также независимые uniforms и загрузку костей.

Сравните неподвижную сцену с большим числом видимых непрозрачных Studio-моделей, например северную комнату `studio_test`, при `r_studio_queue 0` и `1`. Сохраните положение камеры, настройки шейдеров, материалов и монитора. Проверьте число пакетов, длину серий и привязки программ, затем сравните время CPU/GPU. Причина remap означает, что очередь отправлена перед моделью с изменяемым скином. Причина resource означает отправку перед изменением ресурсов.

`cl_perf_batch 1` показывает пакеты моделей в общих сериях и одиночные пакеты, сгруппированные и одиночные диапазоны мешей, а также число сэкономленных вызовов рисования. Секция работает независимо при `cl_perf 0`: собираются только счетчики, без постоянных встроенных измерений этапов CPU и GPU-запросов. Заголовок обозначает суммы по последним завершенным принятым кадрам Host, до восьми кадров, включая пустые. `cl_perf_batch 0` скрывает секцию отдельно.

`cl_perf_batch 2` непрерывно измеряет затраты CPU и обновляет то же окно после каждого завершенного принятого кадра Host. Окно содержит до восьми кадров и обновляется также при `cl_perf 0`.

Заголовок CPU обозначает средние значения: `ms/frame` равно суммарному времени операции, деленному на число кадров окна; `us/call` равно этому времени, деленному на число вызовов операции, а `Calls total` показывает сумму вызовов за окно. Таблица уровня 2 показывает сохранение и восстановление GL-состояния, привязки программ и буферов, загрузку костей. `Top detail` показывает самый затратный подробный этап, если для него есть измерения.

`perf_dump` отдельно измеряет следующий полный принятый кадр Host и автоматически выводит результат после завершения. Без подключенного просмотрщика Tracy подробные замеры Studio выключены между запросами на уровнях батчинга 0/1; на уровне 2 они остаются активными. Захват измерений CPU при `cl_perf 0` не включает GPU-запросы. Результат одного кадра хранится отдельно от постоянно обновляемой таблицы батчинга. Вложенные фазы сохранения и восстановления и пять этапов подготовки и отправки Studio доступны в дампе. Единицы и границы измерения описаны в [счетчиках батчинга Studio](performance-monitor.ru.md#счетчики-батчинга-studio).

## Запись фаз при воспроизведении демо

`r_studio_phases_start <name> [first_demo_frame last_demo_frame]` включает ожидание записи фаз в диапазоне кадров демо с обеими границами. Выполните команду перед `timedemo`, затем вызовите `r_studio_phases_stop` и `r_studio_phases_export [name]` после воспроизведения. Команда `r_studio_phases_status` показывает активность, число сохраненных видов и переполнение. Загрузка до первого записанного вида сохраняет ожидание. Сброс сессии или контекста после начала записи останавливает сбор и сохраняет данные. Прерванный вид имеет `complete=0`.

Сбор по умолчанию выключен. `StudioDiagnostics` владеет `StudioPhaseCapture`; рендерер и отправка передают числовые результаты нагрузки. По умолчанию заранее выделяется место для 16384 видов при общем пределе памяти 128 MiB. Исчерпание емкости видов или стека вложенности из восьми уровней останавливает сбор и отражается в `overflow` и `dropped`. Длинные демо следует разделять на диапазоны с обеими границами, а незавершенные виды исключать из сравнений. Итоговый timedemo FPS измеряется с выключенным сбором фаз.

Экспорт выполняется вне измеряемого цикла и записывает `<gamedir>/studio_diagnostics/<name>.phases.csv`, затем `<name>.phases.metadata.json`. Metadata служит маркером завершения. Ошибка записи или публикации сохраняет данные в RAM для повторной попытки. Запись сбрасывается после успешного экспорта.

Схема фаз `2` содержит `view_id,host_frame,render_frame,output_id,demo_frame,client_time,old_client_time,view_cpu_us,frame_interval_us,opaque_cpu_us,transparent_cpu_us,world_cpu_us,packets,draws,meshes,triangles,complete,physical_draws,submitted_triangles`. Время указано в микросекундах. `frame_interval_us` измеряет интервал между началами записанных видов; остальные интервалы относятся к своему виду. Вложенные виды сохраняют отдельные времена проходов и счетчики. `packets` считает опубликованные пакеты, `draws` считает логические группы пакетов, `meshes` считает входящие в них меши, а `triangles` считает выбранную геометрию. `physical_draws` считает фактические вызовы GL. В `submitted_triangles` также входят диапазоны частей тела, отвергнутые union instancing.

Сопоставляйте прогоны по кадру демо и времени клиента. `view_id` принадлежит записи; `host_frame` и `render_frame` берутся из счетчиков движка. `output_id=0` означает отсутствие доступного идентификатора. Metadata содержит имя демо, первый и последний записанные кадры и время клиента, число завершенных видов, пределы памяти, переполнение, число пропущенных видов и причину остановки.

## Запись описания кадра

```text
r_studio_dump render_check
```

Команда включает запись следующей сцены в `<gamedir>/render_check.txt`. Дамп содержит вызовы отправки, выбранный путь, причины возврата в движок, числа мешей и материалов, параметры освещения и режима отрисовки.

```text
r_studio_dump render_lights lit
```

Вариант `lit` ожидает кадр с источником света сущности, чтобы его параметры попали в дамп.

## Сравнение изображений

Зафиксируйте сцену, затем выполните:

```text
r_studio_ab render_compare
```

Команда снимает движковый и шейдерный пути в двух кадрах, сохраняет `render_compare_off.tga` и `render_compare_on.tga` в `<gamedir>`, затем восстанавливает настройки шейдеров и материалов. Авторские материалы отключаются в обоих кадрах, чтобы их оформление не определяло результат сравнения. Движение между кадрами может дать различия, не связанные с рендером. Команда требует загруженную карту и не запускает вторую запись, пока первая не завершена.

При оценке различий учитывайте обработку fullbright и пропуск штатных плоских теней в шейдерном пути. Эти ограничения описаны в документе об устройстве рендера.

`r_studio_rigid_stats [reset]` показывает накопленные физические вызовы, логические группы пакетов, логические и отправленные треугольники, батчи, сэкономленные вызовы, объем и число загрузок и причины fallback. Счетчики сохраняют 64-битные значения. Union instancing отправляет все диапазоны частей тела и отсекает невыбранные; логические треугольники учитывают выбранную геометрию.

## Чтение счетчиков производительности

```text
cl_perf 3
perf_dump
```

Монитор различает следующие счетчики:

| Счетчик | Значение |
|---|---|
| Studio shader submissions | Вызовы для частей тела, принятые шейдерным путем. |
| Studio engine submissions | Вызовы, переданные штатному движку. |
| Studio draw calls | Физические вызовы `glMultiDrawElements` или `glDrawElementsInstanced`. |
| Studio constituent draws | Число обычных диапазонов индексов или логических экземпляров в этих вызовах. |
| Studio triangles | Сумма количеств отправленных индексов, деленная на три. |

Для измеренной выборки с ненулевым `Studio draw calls` отношение constituent draws к draw calls дает среднее число логических диапазонов или экземпляров на физический вызов. Вызов с 6 и 9 индексами дает один вызов API, два диапазона индексов и пять треугольников.

Studio CPU включает подготовку и отправку. Измерение Studio GPU охватывает вызовы шейдерной геометрии. Уменьшение счетчиков само по себе не доказывает рост FPS. Сравнивать время CPU и GPU следует на одной сцене, с одинаковыми материалами и настройками монитора.

Сценарии для игры и покрытие автоматических тестов приведены в [проверке рендеринга Studio](testing/studio-rendering.ru.md).

## Подготовка встроенных шейдеров

Исходники шейдеров, общие GLSL-файлы и манифесты встроены в модуль. Программы компилируются при создании GL-контекста и сохраняются в памяти до его завершения.

Для сообщений стартовой компиляции используется параметр запуска `-dev`. Параметр `-noshaderwarmup` переносит компиляцию на первое использование программы.
