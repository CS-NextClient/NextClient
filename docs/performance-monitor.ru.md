# Мониторинг производительности

[Английская версия](performance-monitor.md)

Описание осей, цветов, `avg`/`p99`/`max` и примеры интерпретации медленных кадров приведены в [справочнике по графикам](performance-graphs.ru.md).

## С чего начать

Встроенный монитор доступен в Release-сборках. Для включения выполните в консоли игры:

```text
cl_perf 2
```

В правом верхнем углу появятся графики CPU и GPU. Для числовых таблиц задайте `cl_perf 1`, для отключения основного монитора задайте `cl_perf 0`. Дополнительные блоки сети, карты и батчинга управляются отдельно, как описано ниже.

## Управление панелью

| Настройка | Значения |
|---|---|
| `cl_perf` | `0`: сбор данных о производительности выключен; `1`: числовые таблицы; `2`: сгруппированные столбчатые графики CPU/GPU; `3`: восемь отдельных графиков. По умолчанию: `0`. |
| `cl_perf_gpu` | `0`: измерения GPU выключены; `1`: измерения GPU включены, если поддерживаются. По умолчанию: `1`. |
| `cl_perf_net` | `1`: сетевая статистика включена. По умолчанию: `0`. |
| `cl_perf_map` | `1`: число полигонов и брашей, позиция, углы и точка взгляда; `2`: имя, свойства и обводка объекта в локальной игре через `map`, иначе режим 1. По умолчанию: `0`. |
| `cl_perf_batch` | `1`: сводка батчинга Studio; `2`: сводка и подробные затраты CPU. По умолчанию: `0`. |

Сеть, диагностика карты и батчинг Studio также работают при `cl_perf 0`. Эти настройки действуют в текущем сеансе игры. При `developer 1` в левом верхнем углу главного меню и меню паузы доступны кнопки производительности, сети, батчинга моделей и сведений о карте. Каждое нажатие переключает следующий поддерживаемый режим из таблицы. Подпись показывает текущий режим и обновляется при изменении cvar через консоль. Индикатор показывает текущее значение `developer`; `developer 0` скрывает панель. Кнопка редактора материалов доступна из главного меню без подключения к серверу.

`perf_dump` измеряет следующий полный принятый кадр Host и автоматически выводит подробные данные CPU вместе со снимками производительности, сети и диагностики карты; `perf_reset` очищает их историю и счетчики текущей сцены.

## Масштаб и оформление

`cl_perf_scale 1` задает базовый масштаб по умолчанию со шрифтом 14 пикселей. Положительные значения задают множитель от 0.5 до 3; `cl_perf_scale 2` дает шрифт 28 пикселей. `cl_perf_scale 0` выбирает автоматический масштаб по высоте области рисования с опорным разрешением 1600×1200. Максимальный автоматический масштаб составляет 2 относительно базы. Шрифт, интервалы и поля графиков соответствуют масштабу; панель остается в границах окна. Столбцы кадров CPU/GPU и сетевых пакетов сохраняют ширину один физический пиксель; число позиций их окон определяется шириной полей после масштабирования.

## Кадры и измерения

GoldSrc обрабатывает кадр во внешнем вызове `Host_Frame`. Монитор считает кадр Host принятым, когда `Host_FilterTime` разрешает продолжить обработку. Выходной кадр (Output) соответствует обмену буферов главного окна через `SDL_GL_SwapWindow`. Один кадр Host может создавать несколько выходных кадров. Обмен буферов также может происходить вне обработки Host.

Swap Interval показывает время между завершенными обменами буферов главного окна. FPS в заголовке рассчитывается по положительным интервалам, завершённым за последние 0,5 секунды, и обновляется каждые 250 мс. Число интервалов делится на их суммарную длительность. Таблицы длительности панели используют текущее окно из N кадров; FPS в `perf_dump` использует его диагностическую временную историю. Host Frame включает обработку принятого кадра до возврата из внешнего вызова `Host_Frame` и его подписчиков. Swap измеряет обмен буферов внутри принятого Host, суммируя несколько обменов.

Render охватывает команды GPU для рендеринга экрана и панели до показа кадра. Измерения CPU/GPU для Studio и радара могут пересекаться с охватывающими их измерениями кадра.

Все три режима производительности показывают `History | last N frames`: таблицы и графики используют одни и те же последние N позиций кадров. N зависит от физической ширины поля панели и может меняться при смене режима, масштаба или разрешения. Порядок позиций CPU/GPU, пропуски и запоздалые результаты описаны в [справочнике по графикам](performance-graphs.ru.md#покадровые-столбцы-и-статистика).

Основные числовые сводки обновляются каждые 250 мс. Таблица батчинга обновляется после каждого завершенного кадра Host. Диагностика карты использует последний отрисованный вид, новые сетевые данные появляются при следующем представлении кадра. Панель рисуется при каждом представлении кадра с последними значениями каждой секции.

Показатели CPU/GPU `avg`, `p99`, `max` используют корректные измеренные значения внутри текущего окна из N кадров. Отсутствующие, ожидаемые и неактивные значения не учитываются. p99 по ближайшему рангу появляется после 100 корректных измерений этой серии внутри окна. Сохраненная история ограничена числом записей; при низком FPS N позиций могут охватывать больше десяти секунд. Нижняя строка Monitor CPU использует то же окно из N кадров.

Статистика истории и FPS в `perf_dump` используют отдельное десятисекундное диагностическое окно; p95/p99 для Swap Interval и флаг percentiles относятся к этой диагностической истории. Монитор проверяет готовность результатов GPU без ожидания их завершения. Строки проходов показывают номер кадра, к которому относится результат, и число выводов кадра, прошедших после него.

Таблицы длительности CPU/GPU показывают `avg`, `p99`, `max`. Время родительского этапа включает время вложенных измеряемых этапов, поэтому наложенные столбцы и строки таблицы нельзя складывать для получения полного времени кадра. Полные правила для групп CPU/GPU, пропусков данных, поздних результатов GPU и отдельных графиков описаны в [руководстве по чтению графиков](performance-graphs.ru.md). Нижняя строка Monitor показывает средние затраты монитора за то же окно из N кадров; дерево этапов, проходы GPU, счетчики и фоновые отчеты доступны в `perf_dump`.

Состояние `Measured` включает корректные измерения с нулевой длительностью. `Inactive` означает, что этап не выполнялся. `Pending` означает ожидание результата GPU. `Unavailable` означает, что измерение не поддерживается либо в движке не определены точки начала и конца этапа. `Dropped` обозначает исчерпание емкости сборщика, `Incomplete` обозначает неполное измерение.

Панели производительности, батчинга Studio, сети и диагностики карты оформлены одинаково. Заголовки разделов выделены цветом, заголовки таблиц имеют фон. Отступы и разделители перед итоговыми строками согласованы между панелями. История и диагностические примечания выделены приглушённым цветом. Цвета числовых рядов и графиков обозначают одни и те же показатели. Числовой режим показывает компактные таблицы `avg`, `p99`, `max`.

Панель расположена у правого верхнего края. `cl_perf_background_alpha` задает непрозрачность подложки от `0` (полностью прозрачная) до `1` (непрозрачная). Значение по умолчанию равно `0.2`. Эта переменная также пропорционально меняет непрозрачность фона графиков и применяется сразу. Значения за пределами диапазона ограничиваются его границами; неконечные значения заменяются значением по умолчанию. Заголовки секций и таблиц сохраняют свои акцентные цвета. В Windows используется Consolas со сглаживанием, без растягивания растровых символов, с тенью в один пиксель.

Панель рисуется перед обменом буферов главного окна, в том числе в меню и при `hud_draw 0`. Ее собственное время CPU отображается как Monitor CPU. Строки CPU в `perf_dump` показывают полное время этапа, собственное время без вложенных этапов и число вызовов. Строки GPU описывают интервалы команд, включая простой GPU между ними. Длительности компиляции и линковки показывают последний измеренный вызов каждой операции.

Для проверки в работающем движке установите `next_engine_mini.dll`, `nitro_api2.dll` и `client_mini.dll`, собранные из одного состояния исходников в производственной конфигурации. Проверки в установленной игре выполняет разработчик. Тестовые конфигурации собирают engine_mini как статическую библиотеку для тестов без движка.

`CPU frame` обозначает завершенный кадр Host, которому принадлежат строки CPU. `Output` и его `Host` обозначают последнее представление кадра; вывод экрана вне Host имеет номер Host 0. Во время следующего вызова Host эти номера могут различаться. Время компиляции, которое еще не измерялось, имеет состояние `Unavailable`; измеренный ноль имеет состояние `Measured`.

Прерывание через `Host_EndGame` или `Host_Error` отбрасывает незавершенное измерение Host и открытые измерения CPU/GPU. Внешняя граница `Host_Frame` восстанавливает сбор для следующих кадров. Ожидающий запрос `perf_dump` повторяет захват на следующем полном принятом кадре Host.

При смене карты незавершенные результаты GPU исключаются, а текущие строки подсистем очищаются. История процесса сохраняется. Изменение размера окна сохраняет запросы того же GL-контекста. Замена контекста создает новое поколение; имена запросов старого контекста сбрасываются без GL-вызовов, если контекст больше не является текущим. Измерение интервалов представления продолжается, пока сохраняется то же окно SDL, поэтому задержка загрузки остается в истории.

## Счетчики батчинга Studio

Секция батчинга управляется независимо от графиков производительности:

```text
cl_perf 0
cl_perf_batch 1
```

`cl_perf_batch 1` показывает сводку из семи строк по последним завершенным принятым кадрам Host, до восьми кадров. `cl_perf_batch 2` непрерывно измеряет подробные затраты CPU Studio за то же окно, в том числе при `cl_perf 0`. Пять категорий расположены в постоянном алфавитном порядке по названию операции CPU. Оба уровня обновляют таблицу при каждом показе кадра по последнему завершенному Host. Пустые кадры входят в окно; отфильтрованные вызовы Host и выводы кадра вне Host в него не входят.

Пока окно заполняется, заголовок показывает фактическое число кадров. Смена уровня, карты и сброс очищают окно. Кадр со сменой уровня исключается. Уровень 0 скрывает блок и используется по умолчанию. Уровень 1 не включает подробные CPU-замеры; при `cl_perf 0` оба уровня не создают GPU-запросов. На уровне 2 непрерывные замеры добавляют затраты на сбор данных.

Команда `perf_dump` измеряет следующий полный принятый кадр Host в текущей сцене. Результат печатается автоматически перед следующим обменом буферов главного окна после завершения измеряемого кадра Host. Захват работает при любых уровнях `cl_perf` и `cl_perf_batch` и сохраняет их настройки. Повторный запрос не перезапускает незавершенный сбор. `perf_reset`, смена карты и выход отменяют запрос и очищают сохраненный результат. Отклоненный или вложенный вызов Host не завершает сбор.

Замер CPU явно отделен от общей истории и асинхронных результатов GPU. Команда требует доступных колбэков кадров Host и вывода кадра в главное окно; при их отсутствии выводится сообщение о недоступности сбора.

В широком окне секция батчинга находится слева от основной панели. Подробный блок занимает 17 строк; в узком или низком окне остаются сводка и самый затратный измеренный вложенный участок. При отсутствии вложенных измерений показывается самая затратная крупная категория GL. Основные режимы производительности сохраняют свою компоновку. `cl_perf 0` отключает их сбор, но секция батчинга остается видимой при ненулевом `cl_perf_batch`. Значение `cl_perf_batch 0` скрывает ее. Секция также работает вместе с независимыми блоками сети и диагностики карты.

Таблица показывает `Grouped`, `Single`, их общее число `Total` и долю объединения. Счетчики относятся к указанному окну кадров. Фон заголовков и горизонтальные линии разделяют таблицу счетчиков, экономию вызовов, затраты CPU и итоговые строки. Подпись `totals` в заголовке обозначает суммы счетчиков за указанное число кадров. Строки таблицы описывают разные показатели:

| Поле | Значение |
|---|---|
| Model draws | Пакеты с копиями мешей, позы и параметров модели. Пакеты `Grouped` отправляются в одном батче с другими пакетами; пакеты `Single` отправляются отдельно. Доля `Grouped %` рассчитывается по всем отправленным пакетам. Одна сущность может создавать несколько пакетов. |
| MultiDraw meshes | Совместимые диапазоны мешей одного пакета. Диапазоны `Grouped` входят в вызовы с двумя и более диапазонами; `Single` входят в одиночные вызовы. Знаменатель доли: все шейдерные диапазоны мешей. |
| Draw calls saved | Разность числа диапазонов мешей и фактических шейдерных вызовов рисования, деленная на число диапазонов. Показатель отражает сокращение вызовов API. Высокая доля объединенных пакетов не означает такое же сокращение вызовов рисования. |

Перед отправкой батча GL-состояние вызывающего кода сохраняется один раз, после отправки восстанавливается. Внутри батча программы и буферы могут меняться. Каждый пакет содержит собственную позу и значения параметров шейдера. Счетчики относятся к принятым кадрам Host, указанным в заголовке, до восьми кадров. Основные таблицы производительности и графики используют общее окно последних N кадров. При отсутствии знаменателя выводится `-`.

Уровень 2 разделяет следующие непересекающиеся категории CPU:

| Строка панели / этап дампа | Измеряемая работа |
|---|---|
| GL save / GL state save | Захват растрового состояния и матриц модели, а также состояния вызывающего кода и стеков GL в начале батча. |
| GL restore / GL state restore | Полное восстановление в конце батча, включая программу, VAO, буферы, текстуры и матрицы. |
| Program bind | Фактический `glUseProgram` при отправке. Повторные привязки, исключенные благодаря кешу, и восстановление программы вызывающего кода не входят. |
| Buffer binds | Привязка bone UBO в начале батча и смена VAO при отправке. Восстановление привязок учитывается в GL restore. |
| Bone upload | `glBufferSubData` для сохраненного числа костей модели; при наличии материала с программой, отличной от `studio_legacy`, сохраняется полная загрузка 128 костей. |

`ms/frame` показывает полное время категории CPU, деленное на число кадров в заголовке. `us/call` показывает среднее время на вызов; `Calls total` содержит сумму вызовов за интервал CPU. Подпись `averages` в заголовке CPU относится к двум столбцам времени. Строка с наибольшими суммарными затратами на кадр выделяется цветом. Порядок строк задаётся названием операции и сохраняется при изменении времени или доступности замеров. Заголовок `CPU live` обозначает текущее короткое окно. Каждый завершённый Host обновляет его суммы. До первого полного кадра выводится `CPU live: waiting for frame`.

Сохраненный однокадровый результат `perf_dump` хранится отдельно от постоянно обновляемой таблицы.

`perf_dump` записывает следующие подробные этапы CPU за один измеряемый кадр:

| Родитель | Вложенный этап | Граница измерения |
|---|---|---|
| GL state save | Model state capture | Захват растрового состояния и матриц для отрисовки модели. |
| GL state save | Batch state save | Привязки вызывающего кода и стеки GL перед отправкой, а также текстурные привязки материалов перед их первым изменением. |
| GL state restore | Restore bindings | Восстановление VAO, bone UBO, общей привязки UBO, программы и array buffer. Привязка array buffer сохраняет исходное место после восстановления атрибутов, поэтому категория вызывается дважды на батч. |
| GL state restore | Restore matrices/attributes | Стеки матриц, режим матриц и `glPopAttrib`. |
| GL state restore | Restore textures | Привязки текстур материалов и базовой текстуры движка. |
| Studio | Model data preparation | Сохраненные данные костей, модели и освещения, записи мешей и массивы диапазонов для отправки. |
| Studio | Mesh sorting | Создание порядка индексов мешей и стабильная сортировка. |
| Studio | GL state apply | Применение растровых параметров и матриц при отправке модели и группы мешей. |
| Studio | Uniform setup | Стандартные uniform-параметры модели и группы, настройка программы. |
| Studio | Texture setup | Привязка базовой текстуры перед рисованием и сброс привязок текстур материалов после него. |

Пять прямых дочерних этапов Studio не включают отправку очереди, подготовку геометрии и материалов, MultiDraw, сохранение и восстановление GL. Настройка параметров авторских материалов сохраняет отдельный замер Material preparation. Работа, которая не вошла в эти категории, остается в собственном времени Studio.

В компактной панели добавляется только `Top detail`: вложенный участок с наибольшим корректно измеренным временем на кадр CPU. Полный список остается в `perf_dump`; уровень 1 его не показывает. При явном подключении внешней трассировки замеры ее инструментированных участков продолжаются. `Other Studio` складывает пять прямых дочерних категорий Studio и оставшееся собственное время Studio. Вложенные этапы сохранения и восстановления GL в эту сумму не входят. Время родителя и дочернего этапа нельзя складывать между собой.

Подготовка геометрии, материалов и Shader submission сохраняются отдельными этапами дампа. Shader submission охватывает MultiDraw и его учет. Отсутствующие и неполные измерения отображаются как `-`, измеренный ноль остается `0.000`. Это время выполнения участка на CPU, включая ожидания драйвера и затраты на измерение.

Дамп показывает, что вызвало отправку накопленной очереди или немедленную отправку пакета. В нем также указаны размеры батчей, привязки программ, вызовы штатного рендерера и все пять этапов CPU. Причины немедленной отправки считаются по пакетам, причины отправки очереди считаются по батчам. Одна такая причина может завершить большой батч из нескольких пакетов. Интервал `r_studio_info` начинается с последнего непрозрачного обхода. Управление и сравнение описаны в [диагностике Studio](renderer-diagnostics.ru.md). Публичный интерфейс имеет версию `PerformanceMonitor001`; движок и клиент необходимо пересобирать вместе.

## Дополнительные блоки сети и диагностики карты

```text
cl_perf 2
cl_perf_net 1
cl_perf_map 1
```

`cl_perf` управляет панелью производительности. Сеть (`cl_perf_net`), батчинг Studio (`cl_perf_batch`) и диагностика карты (`cl_perf_map`) собирают и показывают данные независимо, в том числе при `cl_perf 0`. Масштаб и прозрачность панелей также действуют при выключенной производительности. Ширина сетевой панели и число позиций ее окна пакетов сохраняются при переключении режимов производительности.

Каждый включенный мониторинг имеет собственный фон и видимый зазор до соседних панелей. Панели заполняются от правого верхнего угла вниз в порядке: производительность, сеть, батчинг Studio, диагностика карты. Если следующий блок не помещается, он переносится наверх колонки слева. Последующие блоки не возвращаются в предыдущую колонку. Число колонок ограничено шириной окна. В последней колонке резервируется место для базовых строк оставшихся панелей; сетевые графики имеют приоритет перед расширенными подробностями. Если места достаточно только для заголовков, названия панелей сохраняются.

Для самостоятельной сетевой панели используйте `cl_perf 0` и `cl_perf_net 1`. Чтобы вернуть штатное отображение сети, задайте `cl_perf_net 0`: исходное значение `net_graph` сохраняется. Штатный график также остается доступен, если новый блок не помещается или отсутствует необходимый перехват показа кадра. `cl_perf_map 0` скрывает диагностику карты и обводку объекта. Определения счетчиков и доступные свойства приведены в [диагностике карты](performance-limits.ru.md).

Сетевые графики используют окна последних N пакетов: число позиций определяется физической шириной графика. Размеры In/Out имеют независимые окна; задержка и маркеры loss/choke используют входящие порядковые номера. Одинаковая горизонтальная позиция в разных окнах может относиться к разным моментам.

Таблицы задержки и размера пакетов показывают `avg`, `median`, `max` по корректным значениям текущего окна. Сводные строки In/Out показывают KiB/s и пакеты в секунду по выборкам с интервалом 100 мс. Оси, пропуски и маркеры потерь описаны в [справочнике по сетевым графикам](performance-graphs.ru.md#пакетные-графики-сети).

## Диагностическая запись Tracy

Диагностическая конфигурация Release использует общий клиент Tracy 0.14.1. Пресет настройки: `ninja-profiler`, пресет сборки: `ninja-profiler-release`. Ее файлы находятся в `build/ninja-profiler/out/bin/Release`. Обычные производственные файлы Windows находятся в `out/bin/Release`. Файлы Linux находятся в каталоге выбранной конфигурации сборки. Каждая команда сборки указывает одну цель:

```text
cmake --preset ninja-profiler
cmake --build --preset ninja-profiler-release --target engine_mini
```

Для диагностики требуется отдельная установка игры с согласованными launcher, NitroApi, движком, клиентом и `TracyClient.dll`. Цель `BUILD_ALL` устанавливает общий клиент только при `USE_PROFILER=ON`. Внешний просмотрщик должен соответствовать закрепленной версии клиента. Он запускается отдельно от игры x86. Подключение активирует области CPU, числовые показатели и GPU-запись. `cl_perf 0`, `cl_perf_gpu 0` и `perf_reset` независимо управляют встроенным монитором. При подключенном просмотрщике дамп показывает `trace=1`.

При прерывании Host открытые области CPU закрываются в обратном порядке вложенности. Затем трассировка продолжается для следующих вызовов Host.

Все доступные CPU-этапы `perf_dump` представлены отдельными областями Tracy. В них входят подробные этапы Studio: сохранение и восстановление GL, смена программы, привязки буферов, передача костей, подготовка, сортировка, применение состояния, параметры шейдера и текстуры. Существующие GPU-этапы представлены областями GPU. Маркеры Host и Output позволяют сопоставить симуляцию и показ кадра. Подключение Tracy автоматически включает этот сбор данных.

Области CPU и GPU сохраняют файл, функцию и строку начала замера. Обёртки Studio и радара передают это место вызова; перехваты штатного движка указывают на место регистрации в коде интеграции. Разные места вызова одного этапа сохраняют отдельные координаты исходного кода. Для использования этих данных создайте новую запись с согласованными DLL движка и клиента.

Счетчики рендеринга и батчинга отображаются графиками Tracy под именами из дампа. При подключенном просмотрщике значения публикуются один раз на принятый кадр Host перед его маркером. Счетчики отрисовок сбрасываются для каждого кадра; диагностические счетчики пропусков и устаревших результатов GPU сохраняют накопительные значения. Собственные области GPU в Tracy и встроенный сборщик GPU управляются независимо.

Дополнительные области диагностики: `Studio client model callback`, `Studio client player callback`, `Studio follow traversal`, `Studio parent pose`, `Server message parsing`. Клиентские области охватывают полный вызов колбэка исходного рендерера, включая вызовы моделей, игроков, viewmodel и вызовы только для подготовки, проходящие через обертки. В часть времени без отдельных замеров могут входить анимация, расчет костей, освещение и другая работа клиента. Передача костей в GPU измеряется существующей отдельной областью.

Обход follow включает колбэки родительской и дочерней моделей. Обработка команд, предсказание и внутренние операции интерфейса закрытого движка измеряются только в пределах доступных точек перехвата.

События передаются потоково во внешний просмотрщик, который хранит запись. Все инструментированные модули используют общий лимит памяти 128 МиБ для очередей событий и связанных буферов. Учет включает округление до единицы выделения памяти на соответствующей платформе. Небольшие начальные очереди растут по мере необходимости и повторно используют освобожденные блоки. При отсутствии событий поток передачи проверяет очередь каждые 2 мс. При приближении к лимиту памяти он отправляет накопленный буфер.

Запись останавливается, если просмотрщик перестает принимать события и очередь достигает лимита памяти. Ошибка выделения памяти для очередей или буферов событий также останавливает запись. Повторное подключение становится доступно после перезапуска игры. Игра и встроенный мониторинг продолжают работать. `perf_dump` показывает текущий расход, максимум, лимит и причину остановки. Значение `stopped=0 reason=none` означает, что запись доступна. Лимит распространяется на очереди и буферы событий. Метаданные символов, фиксированные буферы среды Tracy и остальная игра выделяют память отдельно.

Области Host в Tracy охватывают весь вызов, включая отфильтрованные вызовы. Маркеры кадров Host обозначают принятые вызовы. Основная серия Frames и именованная серия Output обозначают завершенные обмены буферов главного окна. `Simulation delta ms` показывает шаг симуляции движка отдельно от интервалов представления кадра. При диагностической инициализации GL выполняется однократная калибровка времени GPU. Адаптер владеет отдельным пулом запросов. Сборщик читает только готовые результаты. Если пул заполнен, новые замеры не начинаются. Запросы, зарезервированные для завершения уже начатых замеров, сохраняются.

Launcher запускает Tracy вне инициализации DLL и останавливает после завершения рабочих потоков, до выгрузки инструментированных DLL. Обработка `Sys_Error` завершает рабочие потоки и профайлер до передачи фатального вызова; такая запись может содержать незавершенные области главного потока. В Windows значение `TRACY_NO_DBGHELP_INIT_LOAD=1` применяется по умолчанию, если оно не задано явно. Загрузка символов модулей выполняется по мере необходимости.

Проверки и пределы покрытия приведены в [документе для разработчика](testing/performance-monitor.ru.md).

Подробные строки CPU в `perf_dump` описывают захваченный принятый кадр Host. Сводка диагностической истории указывает собственное число кадров и интервал. В строке указывается непосредственный родительский этап, если он одинаков для всех вызовов. Этапы, вызываемые под разными родителями, отображаются отдельными суммарными строками; их время пересекается со временем охватывающих этапов.

`perf_dump` показывает стоимость учета входов и выходов CPU-этапов для последнего завершенного Host и опроса GPU-результатов для последнего вывода кадра. Эти затраты входят во время кадра и не прибавляются к Host CPU. Monitor CPU включает подготовку и отрисовку панели, а также опрос после swap. Опрос перед swap уже входит в измерение панели. Измерение накладных расходов добавляет стоимость чтения часов.

GPU-измерения Tracy дополнительно требуют `glGetInteger64v` для калибровки и функции проверки расширений GL. При отсутствии необходимых функций сохраняются CPU-трассировка и асинхронный встроенный сборщик GPU.

## API для разработчика

Публичный тип монитора называется `performance::PerformanceMonitorInterface`. Снимки движка, счетчики, абсолютные показатели, отчеты рабочих потоков и владельцы участков измерения принадлежат `performance`. Общие типы часов, длительности, измерений и учета CPU принадлежат `ncl_perf`. Границы описаны в [правилах владельца монитора](../nextclient/engine_mini/src/performance/AGENTS.md).

### Владение и поток вызова

Владелец подсистемы `performance` существует до выгрузки DLL. Он создает часы перед конкретным классом `PerformanceMonitor`, объявленным `final`, и хранит рядом `PerformanceMapper`. Экспортируемая фабрика возвращает один и тот же монитор в течение всего времени жизни DLL. Композиция рендерера передает потребителям ссылки на этот монитор и `PerformanceMapper`. Внутренние CPU/GPU-замеры вызывают конкретный монитор напрямую; публичные замеры через интерфейс сохраняют контракт между DLL. Глубина вложенных Studio-замеров принадлежит каждому рендереру и используется совместно его перехватчиком и GL-отправкой. Вложенный замер одного рендерера не подавляет замер другого.

`PerformanceRuntime` получает готовые таблицы движка и клиента, необязательные провайдеры SDL и жизненного цикла кадра. Ему также передаются конкретные монитор, `PerformanceMapper`, часы и владельцы устройства рендеринга и его жизненного цикла. `PerformanceRuntime` хранит хуки, подписку на кадры, сетевое состояние, адаптеры GPU и трассировки, панель, снимки и квары со стабильными адресами. Обычные C++-хуки захватывают этот объект. Колбэки C для кваров и консольных команд используют один явно привязанный обработчик. Указатели текущего подключения читаются из переданных таблиц при соответствующем событии.

`OnGameInitializing` передает функцию консольного текста после копирования таблицы движка; локализация в этой фазе может отсутствовать. `OnGameInitialized` затем передает проверенные квары и локализацию. Конструктор панели получает эти зависимости, общий Windows `TextRenderInterface`, часы и слот учета текстуры движка. Отрисовка не ищет сервисы. Панель, созданная до инициализации представления, получает явную привязку при завершении этой фазы. В Linux сохраняется вывод через консольную функцию, когда она доступна.

Завершение работы отключает хуки этапов и обмена буферов, забывает оставшиеся GPU-объекты и запрашивает остановку CPU-части и подписки. Сам `PerformanceRuntime`, его адаптер трассировки, монитор, `PerformanceMapper` и часы продолжают существовать. Вложенный Host сохраняет наблюдателя до выхода из внешнего Host, который сообщает о завершении или прерывании кадра. Завершение работы не уничтожает `PerformanceRuntime` из выполняющегося колбэка.

Перед вызовом штатной цепочки хуков обработчик вида сохраняет идентичность карты, подключения и модели мира, а также внутреннее поколение сессии `PerformanceMapper`. Смена карты и `CL_ClearState` сбрасывают заимствованные данные модели мира. Устаревший внешний обработчик вида завершается, сохраняя новый снимок вложенной сессии. Захват матриц и отрисовка контура проверяют поколение переданного устройства и фактический текущий контекст непосредственно перед GL-операциями.

Интерфейс `PerformanceMonitor001` принадлежит главному потоку движка, который управляет обработкой кадров. Все методы вызываются в этом потоке, включая чтение снимков и поколения карты, запись счетчиков и абсолютных показателей, а также `ReportWorker`. Чтение через const-метод не делает API потокобезопасным. Рабочие потоки возвращают результаты с собственным временем жизни. Их владелец в главном потоке публикует `performance::PerfWorkerReport` через `ReportWorker`. CPU-участки закрываются в обратном порядке вложенности в том же потоке. Для вызовов GPU-участков дополнительно требуется соответствующий действующий контекст рендеринга этого потока.

### Фоновые задачи и интеграция радара

`ClientMini` создает собственный `radar::integration::Performance` с необязательным экспортированным монитором и передает его вместе со средой выполнения задач через `GameHud` в `HudRadarAdvanced`. Конкретные слои, текст и генератор изображений получают прямые ссылки на свои зависимости. `HudRadarAdvanced` владеет адаптером `radar::integration::LayerAnalysis`, а адаптер владеет задачей `RadarLayerAnalysisJob`.

Задача принимает заданный владельцем идентификатор запроса и собственные копии геометрии и ручных поправок. Результат содержит карту, идентификатор запроса и длительность в наносекундах. Необязательный приемник событий задачи получает `Pending`, `Completed`, `Failed` и `Canceled` только в потоке владельца при отправке задания, сбросе и опросе результата. `Pending` означает фактическую отправку задания; замененный вход может получить отмену до отправки. Отмененное задание не публикует последующее завершение или ошибку.

Адаптер назначает возрастающие идентификаторы запросов, сохраняет поколение карты монитора перед запуском каждого запроса, преобразует события в `performance::PerfWorkerReport` и удаляет привязку после конечного события. Отложенная отправка сохраняет поколение, записанное при `Start`. HUD вычисляет диагностическую длительность в миллисекундах из результата.

Сброс отменяет текущие запросы без ожидания. Завершение работы отменяет запросы и дожидается задания, пока существуют адаптер, привязки запросов, владелец измерений и среда выполнения задач. Копирование и перемещение адаптера запрещены, поскольку приемник событий задачи захватывает владельца. Владелец измерений освобождается после явного завершения работы и уничтожения HUD, перед остановкой среды выполнения задач.

`HudRadarAdvanced` владеет конкретным `RadarDrawContext`, включая программы, фоновые буферы, очередь примитивов, состояние GL и счетчики. Подготовка кадра сохраняет дескрипторы текущих контекста и окна; обработчики `GL_SetMode`, удаления SDL-контекста и окна сбрасывают владение перед вызовом исходной функции. Совпадающий текущий контекст разрешает удалить собственные объекты GL. При потере или несовпадении контекста владелец только забывает имена и очередь. Это решение распространяется на изображения и буферы `RadarOverview`/`MapLayerRenderer`; их деструкторы не вызывают GL. `GameHud::Shutdown` отключает колбэки радара, дожидается анализа и освобождает либо забывает графические ресурсы, пока монитор, среда выполнения и провайдеры еще существуют. Текст сбрасывает только собственные данные: атлас принадлежит движку.

### Типы показателей и публикация

Участок измеряет один интервал выполнения и сохраняет сведения о месте вызова. Историческая серия длительностей выбирает измеренные суммы участков или интервалы показа кадров в домене Host либо Output, указанном дескриптором. Аддитивный счетчик суммирует приращения событий в принятом кадре Host. Абсолютный показатель записывает наблюдение через `SetGauge`: повторная запись заменяет текущее ожидающее значение. Значения и сводки таких показателей используют `double` отдельно от длительностей в наносекундах. Дескриптор задает единицу измерения, домен, агрегацию последнего наблюдения, имя в трассировке и строку Studio.

`SetGauge` принимает только конечные значения внутри принятого кадра Host, когда сбор счетчиков включен мониторингом производительности, батчингом Studio, захватом или внешней трассировкой. Неверный идентификатор, нечисловое или бесконечное значение, выключенный сбор либо вызов вне такого кадра возвращают false и сохраняют ожидающее наблюдение. Измеренный ноль учитывается как выборка. Если записи нет, значение кадра остается `Inactive`; пропущенные значения не входят в число измерений, среднее и максимум.

Сброс, смена карты, прерывание Host и отключение сбора очищают ожидающие наблюдения. В историю они попадают только после нормального завершения принятого кадра. Поле `last` сводки выбирает последнее измеренное значение Host в выбранном окне, а `mean` и `maximum` описывают измеренные значения отдельных кадров.

`performance::PerfSnapshot::gauges` содержит значения и состояния последнего завершенного принятого Host, включая неактивный Host после ранее измеренного кадра. Поле `latest` сохраняет идентификатор последнего вывода кадра.

Диагностическая история хранит до 16 384 записей Host/Output и выбирает десятисекундное окно; при достижении емкости доступный интервал может сократиться. Таблица Studio выбирает до восьми принятых кадров Host, включая неактивные, и показывает последнее значение или состояние рядом с `max` выбранного окна. Дамп сохраняет показатель захваченного Host и выводит число измерений, среднее и максимум его истории. Старое измеренное значение сводки не подставляется вместо отсутствующего наблюдения текущего кадра.

`StudioQueuePeakPackets` измеряет максимальное число удерживаемых пакетов за последний завершенный непрозрачный обход. `Studio_EndOpaquePass` сначала отправляет ожидающие данные и опустошает очередь, затем публикует сохраненную статистику `max_run`. Завершенный пустой обход публикует измеренный ноль. Если за один Host завершаются несколько обходов, показатель содержит максимум последнего завершенного обхода. Строка Studio и дамп берут единицу `packets` из дескриптора. Существующие счетчики пакетов сохраняют смысл суммы приращений.

Чтение снимка копирует опубликованное состояние. Публикация обновляется при завершении принятого Host, завершении отдельного вывода кадра и в коде показа панели после опроса GPU и обновления сведений о движке. Текущий показатель Host обновляется при завершении Host; история и числовое окно CPU сохраняют независимый интервал обновления 250 мс. Окно Studio из восьми кадров также обновляется после каждого завершенного принятого Host. Измеренные абсолютные значения передаются в трассировку при фиксации принятого Host, в том числе при выключенном встроенном мониторинге. Неактивный показатель не создает числовую запись трассировки. Код, которому достаточно числовых значений только в трассировке, может продолжать использовать `NCL_PROFILE_VALUE`.

## Интеграция фаз контекста

`performance::runtime::ReleaseContext` освобождает GPU-объекты трассировки и монитора, только если сохраненный дескриптор контекста монитора совпадает с текущим контекстом. При несовпадении монитор забывает старые имена объектов без GL-вызовов. `performance::runtime::AbandonContext` забывает GPU-объекты без GL-вызовов, завершает ожидающие значения GPU как неполные и сбрасывает геометрию панели. Завершенная история CPU и ее интервал накопления сохраняются. Обе фазы отклоняют запоздалое завершение GPU-измерений. Изменение размера в том же контексте сохраняет ожидающие запросы.

`performance::runtime::Shutdown` завершает CPU-часть и подписки после выбранной фазы контекста. Повторный вызов безопасен; резервная очистка забывает имена объектов без GL-вызовов. `performance::PerformanceMonitor::Shutdown` также забывает GPU-объекты до завершения CPU-части. Наблюдатель активного Host и адаптер трассировки остаются доступны до выхода или прерывания текущего колбэка Host. Незавершенный Host не публикуется как полное измерение. Координатор рендерера и SDL-адаптеры выбирают фазу контекста до передачи вызова уничтожения. `performance::FrameSubscription` отключается после обработки выхода из активного внешнего Host в соответствии с [контрактом жизненного цикла NitroApi](../nextclient/nitro_api/AGENTS.md#frame-lifecycle).
