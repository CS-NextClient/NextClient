# Монитор производительности

[Английская версия](performance-monitor.md) | [Архитектура](performance-architecture.ru.md) | [Чтение графиков](#чтение-графиков) | [Проверка](testing/performance-monitor.ru.md)

Монитор показывает, на что игра тратит время: работу движка, рендеринг, радар и другие операции. Он также помогает проверить сетевой обмен и сохранить данные для разбора проблемы. Монитор доступен в Release-сборках.

## С чего начать

Откройте игровую консоль и включите графики:

```text
cl_perf 2
```

Панель появится справа сверху. При сравнении результатов используйте одну и ту же сцену, разрешение, ограничение FPS и настройку VSync. Значения, шкалы и статистика объясняются в разделе [«Чтение графиков»](#чтение-графиков).

## Управление панелью

| Настройка | Значения |
|---|---|
| `cl_perf` | `0`: основной монитор выключен; `1`: числовые таблицы; `2`: общие графики CPU/GPU; `3`: отдельный график для каждого показателя. По умолчанию `0`. |
| `cl_perf_gpu` | `0`: измерения GPU выключены; `1`: включены, если поддерживаются. По умолчанию `1`. |
| `cl_perf_net` | `1`: сетевая статистика. По умолчанию `0`. |
| `cl_perf_map` | `1`: геометрия карты и координаты; `2`: свойства и контур выбранного объекта в локальной игре. На внешнем сервере действует режим 1. По умолчанию `0`. |
| `cl_perf_batch` | `1`: счетчики группировки моделей при отрисовке; `2`: счетчики и подробные замеры CPU. По умолчанию `0`. |

Сеть, диагностика карты и счетчики группировки работают и при `cl_perf 0`. С `developer 1` в главном меню и меню паузы доступны кнопки переключения этих режимов.

`cl_perf_scale` задает масштаб панели от 0.5 до 3; `0` включает автоматический выбор, значение по умолчанию `1`. `cl_perf_background_alpha` задает непрозрачность фона от `0` до `1`, по умолчанию `0.2`. Размер окна влияет на размещение панели и количество видимых измерений.

## Чтение графиков

На иллюстрациях показаны тестовые данные при разрешении 1600x1200 и `cl_perf_scale 1`.

![Группы измерений CPU и GPU](images/performance-monitor/cl-perf-2-example.png)

### Группы измерений

| Показатель | Что измеряется |
|---|---|
| Swap Interval | Время между обновлениями изображения в главном окне, включая ожидание из-за ограничения FPS и VSync. |
| Host Frame | Вся работа движка за кадр: обработка игровых данных, подготовка рендеринга и ожидания. |
| Studio и Radar в CPU | Время работы CPU над моделями и радаром. |
| Swap | Время, потраченное CPU на вывод готового изображения; может включать ожидание GPU или VSync. |
| Render | Время рендеринга на GPU, включая панель монитора. |
| Studio и Radar в GPU | Время отрисовки моделей NextClient и радара на GPU. Штатный рендеринг моделей измеряется только на CPU. |

На графике CPU синий столбец показывает Swap Interval, оранжевый показывает Host Frame. Цветные части показывают Studio, Radar и Swap. На графике GPU полупрозрачный столбец показывает Render, а цветные части показывают Studio и Radar.

Время отдельной операции уже входит в общее время, поэтому эти столбцы и строки нельзя складывать. CPU и GPU работают одновременно, так что сумма их времени тоже не равна времени кадра.

Строка Monitor показывает среднее время CPU, которое занимает сам монитор, включая рисование панели и получение результатов GPU. Среднее рассчитано по кадрам, показанным на графике.

Worker показывает длительность фонового расчета радара. Он выполняется параллельно и не прибавляется к времени основного кадра.

### Кадры на графике

Заголовок `History | last N frames` означает, что показаны последние N кадров. Новые значения появляются справа, предыдущие сдвигаются влево. Ширина одного столбца равна одному физическому пикселю. При изменении размера или масштаба панели меняется N, а вместе с ним и набор данных для статистики.

Каждое обновление изображения занимает отдельное место на графике. Если за один шаг движок обновил экран несколько раз, его время CPU показывается один раз, у последнего обновления. Если экран не обновился, измерение движка занимает отдельное место. Поэтому количество столбцов и количество шагов движка не всегда совпадают.

Таблицы используют те же N кадров, что и графики. При низком FPS они могут охватывать больше десяти секунд. Пустое место слева означает, что данных пока недостаточно, чтобы заполнить график.

Если часть измерений еще не готова, пропущена или не завершена, соответствующий составной столбец не показывается. Неактивная часть дает ноль. Очень короткая операция может занять меньше одного пикселя по высоте и остаться незаметной.

Графики CPU/GPU и их таблицы обновляются каждые 250 мс. Вертикальная ось показывает миллисекунды. Общие графики CPU/GPU имеют одинаковую шкалу, выбранную по самым большим значениям; минимальный диапазон составляет 1 мс. Большой пик может сделать остальные столбцы малозаметными. Для просмотра небольших значений используйте `cl_perf 3`, где у каждого показателя своя шкала.

![Отдельные графики измерений](images/performance-monitor/cl-perf-3-example.png)

### Статистика

В таблицах CPU/GPU показаны `avg`, `p99` и `max` для выбранных N кадров. Пропущенные, неготовые и неактивные измерения в расчет не входят.

| Столбец | Значение |
|---|---|
| `avg` | Среднее арифметическое. |
| `p99` | Значение, которое не превышают 99% измерений. Оно рассчитывается по ближайшему рангу и появляется после 100 измерений показателя. До этого выводится `-`. |
| `max` | Наибольшее значение. |

Каждая строка описывает свою операцию. Например, среднее время Studio уже учтено в среднем времени Host Frame, поэтому складывать строки не нужно. Если операция не измерялась, таблица показывает ее неактивность.

`perf_dump` использует отдельную историю за последние 10 секунд. Для Swap Interval он выводит `p95` и `p99`. `p95` означает, что 95% измерений не превышают это значение. `percentiles=1` появляется, когда в этой истории есть не менее 100 измерений Swap Interval.

FPS в заголовке рассчитывается за последние 0.5 секунды: число положительных интервалов между обновлениями экрана делится на их общую длительность. Поэтому FPS в заголовке и статистика таблицы могут описывать разные отрезки времени. Для сравнения: 60 FPS соответствуют 16.67 мс, 100 FPS соответствуют 10 мс, 144 FPS соответствуют 6.94 мс.

### Почему результаты GPU появляются позднее

GPU может закончить работу через несколько кадров после CPU. До получения результата место на графике остается пустым, затем заполняется. Результат относится к исходному кадру и не сдвигается к моменту получения.

Нехватка места для новых измерений также может привести к пропускам. Проверяйте сообщения о пропусках, прежде чем сравнивать результаты.

GPU age показывает, сколько обновлений экрана прошло после кадра с последним готовым измерением GPU. Нулевое значение само по себе не означает, что измерение доступно: проверьте также наличие результата.

Время Render может включать паузы, пока GPU ждет следующую работу от CPU. Поэтому отключение размытия радара может уменьшить время Radar без такого же уменьшения Render. Для проверки сравните Backdrop capture и Backdrop blur в `perf_dump` и временную шкалу CPU/GPU в Tracy.

По одному значению Swap нельзя определить, что вызвало ожидание: GPU, VSync или драйвер. Сравнивайте его с Swap Interval, Host Frame, Render и текущими настройками VSync и FPS. `cl_perf_gpu 0` отключает измерения GPU во встроенном мониторе.

### Пакетные графики сети

Заголовок `Network | last N packets` означает, что горизонтальная ось считает пакеты. Одна позиция занимает один физический пиксель. Справа появляются новые данные; изменение размера панели меняет N.

Размеры входящих и исходящих пакетов показаны в отдельных последовательностях. Задержка, loss и choke используют последовательность входящих номеров пакетов. Поэтому одинаковая горизонтальная позиция на разных графиках может соответствовать разному времени.

| Показатель | Значение |
|---|---|
| Latency | Задержка в миллисекундах, измеренная после обработки обычного сообщения сервера. Для сообщения, собранного из надежно переданных фрагментов, отдельный замер не создается. |
| Packet size (B) | Размеры входящих (In) и исходящих (Out) пакетов в байтах по данным движка. |
| Traffic | Скорость в KiB/s и число пакетов в секунду; данные собираются с интервалом 100 мс. |
| Loss | Потерянные пакеты, красные отметки под графиком задержки. |
| Choke | Пропуски отправки из-за ограничения скорости передачи, оранжевые отметки. |

Таблицы сети используют `avg`, `median` и `max` для показанных N пакетов. `median` обозначает среднее по порядку значение. Итоги loss и choke показываются в процентах. Позиции с loss или choke не содержат измерения задержки.

Если движок уже удалил старые сведения о пакете, на графике остается пробел. Такой пробел не считается ни нулевой задержкой, ни подтвержденной потерей. Новые сетевые данные отображаются при следующем обновлении экрана. Внизу отдельной сетевой панели указано число сохраненных позиций In и Out.

## Захват кадра

```text
perf_dump
```

Команда измеряет следующий завершенный кадр и выводит в консоль подробные данные CPU, GPU, сети и карты. Она работает и при выключенной основной панели. Если ошибка прервала кадр, команда ждет следующего. Смена карты, сброс монитора и завершение игры отменяют запрос.

В строках CPU полное время `incl` включает вызванные операции, а собственное время `self` исключает их измеренную длительность. Данные GPU могут относиться к более раннему кадру. Сохраняйте номера кадров из дампа, чтобы сопоставить его с записью Tracy.

`perf_reset` очищает историю измерений и данные диагностики карты. Записывайте подробный дамп отдельно от обычного замера производительности: его сбор тоже занимает время.

## Счетчики батчинга Studio

Батчинг объединяет отрисовку нескольких моделей или частей модели, чтобы сократить число обращений к графическому API. `cl_perf_batch 1` показывает счетчики, а `cl_perf_batch 2` дополнительно измеряет время CPU. Таблица охватывает до восьми последних завершенных кадров, включая кадры без Studio-моделей.

| Значение | Как читать |
|---|---|
| Итоги счетчиков и Calls total | Сумма за показанные кадры. |
| `ms/frame` | Среднее время операции за кадр. |
| `us/call` | Среднее время одного вызова операции. |
| Queue peak | Максимальный размер очереди рисования при последней отрисовке непрозрачных объектов; если очередь была пустой, показывается ноль. |
| Экономия вызовов рисования | Насколько группировка сократила число вызовов. Фактическое ускорение проверяется по времени CPU/GPU. |

Порядок сравнения описан в [диагностике рендерера](renderer-diagnostics.ru.md). Дамп одного кадра и таблица нескольких кадров могут показывать разные значения.

## Дополнительные блоки сети и диагностики карты

`cl_perf_net 1` показывает размеры пакетов, задержку, трафик, потери и choke, то есть пакеты, отправку которых сервер пропустил из-за ограничений скорости передачи. Если панель помещается в окне, она скрывает штатный сетевой график, сохраняя его настройку. Подробнее см. [сетевые графики](#пакетные-графики-сети).

`cl_perf_map 1` показывает счетчики геометрии и координаты. Режим `2` добавляет свойства и контур выбранного объекта в локальной игре. Команды описаны в [руководстве по диагностике карты](performance-limits.ru.md).

## Диагностическая запись Tracy

Настройте сборку с профилированием и соберите каждый нужный модуль отдельной командой:

```text
cmake --preset ninja-profiler
cmake --build --preset ninja-profiler-release --target engine_mini
```

Для диагностики подготовьте отдельную установку игры. Launcher, NitroApi, engine, client и библиотека Tracy должны быть собраны с совместимыми настройками. Файлы этого пресета находятся в `build/ninja-profiler/out/bin/Release`. Сборка одного модуля не устанавливает весь комплект; используйте [процедуру установки](testing/installation-and-factory.ru.md).

Используйте просмотрщик Tracy версии 0.14.1, соответствующей клиентской библиотеке в репозитории. Подключение просмотрщика включает запись; `perf_dump` показывает `trace=1`. Настройки встроенного монитора действуют независимо.

В записи найдите медленный кадр и сравните длительности его операций CPU и GPU. Метки Host обозначают работу движка за кадр, Output обозначают вывод изображения. Вложенные операции уже входят в длительность внешней, поэтому складывать их нельзя. Метки `Monitor` показывают затраты самой диагностики.

Сохраните запись в просмотрщике. Если запись остановилась из-за ограничения памяти, для новой записи требуется перезапуск игры. Игра и встроенный монитор продолжают работать. Причина остановки указана в `perf_dump`; аварийный выход может оставить неполную запись.

Запись Tracy помогает найти медленные операции. Итоговую производительность сравнивайте с выключенным профилированием, на одной сцене и с одинаковыми настройками. Сценарии проверки перечислены в [процедуре тестирования](testing/performance-monitor.ru.md).
