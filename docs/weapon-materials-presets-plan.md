# План: пресеты материалов и общее серверное API

Первая версия серверного API была привязана к оружию, к одной таблице на карту, к
четырём слотам и к числовым идентификаторам
([archive/weapon-materials-server-api-plan.md](archive/weapon-materials-server-api-plan.md)).
Здесь описано, чем это заменено и чего замена стоила.

## Состояние на 07.08.2026

Сделано целиком: формат и его разбор с 15 тестами, клиентская загрузка и привязки,
инстансные параметры, тип синхронизации `Material` на обеих сторонах, пять нативов,
тестовый плагин, `matgen check` для пресетов, документы. Прежний формат
(`ncl_material/ServerTable`, сервис `MaterialTable`, сообщение `ncl_mat`) удалён,
а не оставлен рядом.

Не проверено ничего из этого в игре. Обе половины собираются, набор тестов зелёный
(170), но вместе они не запускались ни разу. Итоговое описание для авторов плагинов -
[weapon-materials-server-api.md](weapon-materials-server-api.md).

## 1. Требования

1. Материал можно задать любой сущности, а не только оружию.
2. Четыре слота - произвольное ограничение, его быть не должно.
3. Идентификатор элемента строковый, а не числовой.
4. Пресетов много, каждый - файл, доставляемый через `ncl_upload_file`.
5. Натив назначает материал парой «файл пресета, имя материала».
6. Пресет - это `materials` с именем у каждого материала.

## 2. Что из них следует, помимо очевидного

### 2.1 Слоты исчезают целиком, а не расширяются

Слот существовал потому, что элемент таблицы адресовал одну текстуру модели, а
сущности нужно было несколько материалов сразу, и адресовать их было нечем, кроме
номера. Как только у материала появляется имя, номер не нужен: сущность носит
**множество** материалов, каждый сам знает свою текстуру, повторная привязка того
же имени заменяет, снятие адресуется тем же именем.

То есть пункт 2 решается не увеличением числа слотов, а пунктом 3.

### 2.2 Строковое имя на проводе стоит ровно столько же, сколько числовое

`StringRegistry` уже переводит строки в `uint16` и уже синхронизирует их клиенту -
на нём работает подмена звуков. Пара «идентификатор строки, идентификатор строки»
это ровно тот тип поля, который уже есть: `ARRAY_STRING_ID_PAIRS_DELTA`.

Отсюда привязка на проводе - **пара (путь пресета, имя материала)**, а набор
привязок сущности - массив таких пар с дельта-обновлением. Ни нового типа поля, ни
нового сообщения.

### 2.3 Объявлять пресеты не нужно вовсе

Раз путь пресета едет в самой привязке, клиент узнаёт о файле в тот момент, когда
он впервые понадобился, и тогда же его читает. `ncl_mat_set_table` пропадает:
серверу остаётся доставить файл через `ncl_upload_file` и назвать его в привязке.

Чтение файла происходит при разборе сообщения, а не в кадре отрисовки.

### 2.4 Тип синхронизируемой сущности - отдельный, не `Weapon`

Материалы перестают быть свойством оружия, значит и жить в типе `Weapon` им больше
нельзя. Заводится тип, привязываемый к любому edict'у; `EntitySync::Create`
принимает любой edict и `VisibilityReference::BindEdictPAS`, так что механизм
готов. Оружие продолжает носить свои подмены звуков, материалы едут рядом.

Побочно это чинит несимметричность: сейчас материалы приезжают только на оружие,
хотя рендер применяет их по индексу сущности и про оружие ничего не знает.

### 2.5 Полей становится два вместо восьми

Было: четыре поля под элементы по слотам плюс четыре под их параметры. Станет:

| Поле | Содержимое |
|---|---|
| материалы | пары `(идентификатор пути пресета, идентификатор имени материала)` |
| параметры | пары `(идентификатор ключа параметра, число шагов)`, ключ - `uWear` или `текстура/uWear` |

## 3. Адресация параметров: решено

Параметр относится к сущности и адресуется как «материал, параметр, значение», где
материал называется своей текстурой. Материал сущности однозначно определяется тем,
какую текстуру он одевает: два материала на одной сущности одну текстуру не делят,
иначе один из них всё равно не был бы виден.

Есть перегрузка без материала: тогда значение применяется ко всем материалам этой
сущности, которые объявляют такой параметр инстансным.

```pawn
native ncl_mat_param(entity, const texture[], const name[], steps);
native ncl_mat_param_all(entity, const name[], steps);
```

**На проводе это остаётся парой.** Ключом едет один идентификатор строки, а сама
строка - либо `uWear`, либо `glock_slide.bmp/uWear`. Разделитель `/` безопасен:
имя текстуры в studio-заголовке это имя файла без путей, косой черты в нём быть не
может, а правила допустимости путей её и не пропустили бы.

Такой ключ - это имя, а не упаковка двух чисел в одно: `StringRegistry` для того и
существует, чтобы строки ездили как идентификаторы. Клиент делит строку по
разделителю и применяет либо к одному материалу, либо ко всем.

## 4. Формат пресета

```json
{
    "version": 1,
    "materials": [
        {
            "name": "golden_slide",
            "texture": "glock_slide.bmp",
            "material": {
                "program": "weapon_finish",
                "params": {
                    "uWearMap": { "texture": "materials/masks/wear/blotches.png" },
                    "uUnderlay": { "texture": "materials/surfaces/brass.png" },
                    "uUnderlayTint": [ 1.0, 0.55, 0.1, 1.0 ],
                    "uWear": 0.5
                }
            }
        }
    ]
}
```

- `name` - строковое имя, уникальное внутри файла; им и адресует плагин.
- `texture` - имя текстуры модели, как и было.
- `material` - как и было.
- `model` - **убирается**. Оно означало «умолчание для этой модели на карту», а
  умолчание для модели уже есть и лежит правильнее: в `.mat` рядом с самой моделью.
  Держать два способа сказать одно и то же незачем.

Бюджеты остаются, но становятся ещё и на набор: элементов в файле, различных
текстур в файле, длина пути, плюс потолок на число загруженных пресетов и на общее
число материалов.

## 5. Нативы

```pawn
native ncl_mat_bind(entity, const preset[], const material[]);
native ncl_mat_unbind(entity, const preset[], const material[]);
native ncl_mat_clear(entity);
native ncl_mat_param(entity, const texture[], const name[], steps);
native ncl_mat_param_all(entity, const name[], steps);
```

`ncl_mat_set_table` пропадает.

Пример:

```pawn
public plugin_precache() {
    ncl_upload_file("materials/my_server/skins.mat", "materials/my_server/skins.mat");
}

public give_golden_glock(id) {
    new weapon = rg_give_item(id, "weapon_glock18");

    ncl_mat_bind(weapon, "materials/my_server/skins.mat", "golden_slide");
    ncl_mat_param(weapon, "glock_slide.bmp", "uWear", 21);
}
```

## 6. Что это стоит

Переделывается почти всё, что сделано по серверной части, и часть клиентской.

- `ncl_material/ServerTable` - формат меняется с таблицы на пресет: числовой
  идентификатор уходит, появляется имя, `model` уходит. Пакет и 21 его тест
  переписываются.
- `ServerMaterials` на клиенте - хранение по одному документу заменяется на кэш
  пресетов по пути, привязки становятся набором пар вместо четырёх слотов, поиск
  по индексу сущности сохраняется.
- Синхронизация - новый тип сущности на обеих сторонах, поля с восьми до двух.
- Нативы, `next_client_api.inc`, тестовый плагин, оба документа.

Оценка: примерно как S1-S3 вместе взятые, то есть это не правка, а вторая версия
API. Прежняя нигде не опубликована, обратная совместимость не нужна.

## 7. Игроки и ремап цветов: отдельный шейдер не нужен

Проверено по коду, а не по памяти. Шейдерный путь не привязывает базовую текстуру
сам: перед отрисовкой группы он зовёт **штатный** `StudioSetupSkin` движка
(`StudioDraw.cpp`), и делает это намеренно - в комментарии там записано, что один из
случаев, которые эта функция закрывает, - «скин, который модель ремапит по цвету
игрока, разрешается в текстуру, построенную для конкретной сущности».

Значит базовая текстура, которую сэмплит наша программа на меше игрока, **и есть**
ремапнутая движком текстура этого игрока. Материал ложится поверх неё: ремап решает
цвета, материал добавляет износ, подложку, узор и блик. Спорить им не о чем, и своей
программы под игроков заводить не надо - `weapon_finish` и так берёт за основу
собственный скин модели.

Что при этом стоит знать:

- Материал адресуется именем текстуры из studio-заголовка (`DM_Base.bmp`), а не тем,
  во что её ремапнул движок. Ремап от этого не страдает: он остаётся у каждого
  игрока своим, потому что привязка тоже своя у каждой сущности.
- Ограничение первой версии снимается: дело было в опасении коллизии, а коллизии нет.
  Остаётся вопрос политики, а не техники - разрешать ли плагину одевать чужих
  игроков; это решает сервер, ровно как с подменой моделей.

## 8. Порядок работ

Формат пресета и его разбор с тестами -> клиентская загрузка и применение -> тип
синхронизации на обеих сторонах -> нативы -> тестовый плагин и документы. Первым идёт
пакет, потому что он без движка и покрывается тестами.
