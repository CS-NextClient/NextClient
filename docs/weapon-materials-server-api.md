# Серверное API материалов

Как плагин выдаёт сущности скин. Формат материалов и путь автора описаны в
[weapon-materials-authoring.md](weapon-materials-authoring.md); здесь только серверная
сторона.

Реализация: `NextClientServerApi`, ветка `feature/material-server-api`. Клиентская
половина: NextClient 2.6.0 и новее.

## 1. Из чего это состоит

**Пресет** - файл со списком материалов, у каждого своё имя. Пресетов может быть
сколько угодно. Едет обычной докачкой через `ncl_upload_file`, тем же путём, что и
текстуры: потолок user-message в GoldSrc 192 байта, файл в него не укладывается.

**Привязка** - какой материал какого пресета носит сущность. Это состояние сущности, и
едет оно синхронизацией сущностей - тем же механизмом, которым уже доставляется
подмена звуков оружия.

**Инстансные параметры** - что написано поверх материала у этой конкретной сущности,
например степень износа. Тоже состояние сущности, тот же путь.

Объявлять пресеты не нужно: привязка называет файл, из которого материал взят, и
клиент читает этот файл в тот момент, когда он впервые понадобился.

## 2. Нативы

```pawn
native ncl_mat_bind(entity, const preset[], const material[]);
native ncl_mat_unbind(entity, const preset[], const material[]);
native ncl_mat_clear(entity);
native ncl_mat_param(entity, const texture[], const name[], steps);
native ncl_mat_param_all(entity, const name[], steps);
```

Все возвращают 1 при успехе и 0 при неверных аргументах, записывая причину в лог
модуля. Плагин от ошибки не падает.

### ncl_mat_bind, ncl_mat_unbind, ncl_mat_clear

Одевают и раздевают сущность. Материал называется двумя строками: файлом пресета (тем
путём, каким его видит клиент) и именем внутри этого файла.

**Сущность может быть любой** - оружие, игрок, что угодно с edict'ом. Регистрировать её
заранее не нужно.

Одевается при этом та сущность, чью модель клиент рисует. Обычно это сам edict, но
носимое оружие в Counter-Strike не рисуется вовсе (`EF_NODRAW`, нулевой `modelindex`),
поэтому привязка к нему уезжает на того, кто его рисует: на владельца-игрока, пока ствол
в руках (это и вид от первого лица, и `p_`-модель, которую видят остальные), и на
weaponbox после выбрасывания. Пересчитывается это каждый кадр, так что подбор и выброс
переносят привязку сами, без участия плагина.

**Материалов на сущности может быть сколько угодно.** Каждый знает, какую текстуру
модели он одевает; материал, одевающий ту же текстуру, что и предыдущий, его заменяет.
Слотов нет и номеров нет.

Кто это увидит, плагин не решает: привязка едет вместе с сущностью и достаётся всем,
кто эту сущность видит. Отсюда же следует, что ничего не нужно пересылать вручную - ни
вошедшему в середине раунда, ни вернувшемуся в поле зрения.

`ncl_mat_clear` снимает всё и прекращает синхронизацию сущности.

### ncl_mat_param, ncl_mat_param_all

Пишут одно инстансное значение поверх материала.

Материал адресуется своей текстурой: два материала на одной сущности одну текстуру не
делят, поэтому имя текстуры однозначно указывает на один из них. `ncl_mat_param_all`
пишет во все материалы сущности, которые объявляют такой параметр, - это обычный
случай, когда речь о состоянии вещи целиком («этот ствол потёртый»).

По проводу едет **число шагов, а не значение**. Размер шага объявлен в манифесте
программы на клиенте, и значение вне этой сетки на проводе непредставимо. Итоговое
значение - `шаги * квант`.

Поставляемая программа называется `weapon_finish`, потому что сделана она под покраску
оружия: её слои (узор, обнажаемая подложка, износ, блик по кромкам) описывают именно
ствол. Механизм её ничем не ограничивает, и надеть её можно на любую сущность, но имя
говорит о назначении, а не о допустимой цели.

Инстансных параметра у неё два, оба с квантом 1/32:

| Имя | Что делает | Диапазон | Шагов на весь диапазон |
|---|---|---|---|
| `uWear` | степень износа | 0..1 | 0..32 |
| `uLayerMix` | доля подмешанного узора | 0..1 | 0..32 |

Параметр обязан быть помечен в манифесте как инстансный и быть скаляром; иначе клиент
его не применит.

**Порядок обязателен: сначала привязка, потом параметры.** Значение, пришедшее раньше
привязки, писать некуда. Повторная привязка того же материала сбрасывает написанное
поверх: свежая привязка начинается с материала в том виде, в каком его объявил пресет.

## 3. Файл пресета

```json
{
    "version": 1,
    "materials": [
        {
            "name": "golden_slide",
            "texture": "glock_slide.bmp",
            "material": {
                "program": "weapon_finish",
                "params": {
                    "uWearMap": { "texture": "materials/masks/wear/blotches.png" },
                    "uWearMapTransform": [ 8.0, 8.0, 0.0, 0.0 ],
                    "uUnderlay": { "texture": "materials/surfaces/brass.png" },
                    "uUnderlayTint": [ 1.0, 0.55, 0.1, 1.0 ],
                    "uWear": 0.5
                }
            }
        }
    ]
}
```

Поля материала:

- `name` - строковое имя, уникальное внутри файла; им плагин и адресует материал.
  Регистр не важен ни здесь, ни в нативе.
- `texture` - **имя текстуры модели**, а не файл. Материал принадлежит текстуре: его
  получит каждый меш, который сейчас разрешается в эту текстуру. Имена конкретной
  модели показывает `matgen uv <model.mdl>`, гадать не нужно.
- `material` - то же самое, что лежит в `.mat` рядом с моделью: программа и её
  параметры. Числа - скаляры, массив из четырёх чисел - вектор, `{"texture": "путь"}` -
  картинка.

Значения параметров здесь - это то, с чего привязка начинается; `ncl_mat_param` пишет
поверх.

### Что клиент отвергнет

Проверяет клиент, потому что рисует он; сервер в содержимое пресета не смотрит.

- Версия не 1.
- Два материала с одним именем в одном файле.
- Больше 128 материалов в файле, больше 64 различных файлов текстур, путь длиннее 96
  символов. Превышение отвергает **файл целиком**, а не лишнее: сервер не может узнать,
  что уцелело, а нарисованное не соответствовало бы описанному.
- Недопустимый путь картинки: абсолютный, с `..`, `.`, пустыми сегментами, обратным
  слэшем, двоеточием, управляющими символами, с расширением не `.png` и не `.tga`.
- Материал, чью программу клиент не знает или чей материал не проходит проверку,
  выбрасывается, остальной файл остаётся.

Отдельно: сам файл пресета обязан иметь расширение `.mat` и допустимый относительный
путь, и клиент держит не больше 32 пресетов за сессию.

## 4. Что происходит само

- **Поздние подключения.** Вошедшему уходит всё, что надето на видимые ему сущности.
- **Возврат в поле зрения.** Сущность, ушедшая из PVS и вернувшаяся, приезжает одетой.
- **Уничтожение сущности.** Привязки уходят вместе с ней.
- **Переиспользование индекса.** Сущность отслеживается по edict'у и серийному номеру,
  поэтому новая на месте старой чужого скина не унаследует.
- **Игрок без NextClient или со старым.** Ему ничего не отправляется.

Клиент должен рисовать шейдерным путём (`r_studio_shader 1`), иначе материалов не будет
вовсе - ни серверных, ни своих.

## 5. Игроки

Разрешены наравне с прочими сущностями. Материал складывается с движковым ремапом
цветов команд, а не спорит с ним: шейдерный путь берёт базовую текстуру у штатного
`StudioSetupSkin`, то есть уже ремапнутую для конкретного игрока, и кладёт отделку
поверх. Адресуется такой материал именем текстуры из заголовка модели (`DM_Base.bmp`), а
результат у каждого игрока свой, потому что привязка своя у каждой сущности.

Стоит ли давать плагину одевать чужих игроков - вопрос политики сервера, а не техники.
Отдельно стоит помнить, что `weapon_finish` рассчитан на ствол: на модели игрока он
отработает, но набор его слоёв придуман не под неё.

## 6. Границы

- **Инстансные параметры только скалярные** и только помеченные в манифесте.
- **Наложения (overlays)** объявляются и проверяются, но ещё не рисуются.
- **Потолки**: 16 материалов на одной сущности, 32 пресета на сессию.

## 7. Полный пример

```pawn
#include <amxmodx>
#include <next_client_api>

new const PRESET[] = "materials/my_server/skins.mat";

public plugin_precache() {
    ncl_upload_file(PRESET, PRESET);
}

public give_golden_glock(id) {
    new weapon = rg_give_item(id, "weapon_glock18");
    if (weapon <= 0) {
        return;
    }

    ncl_mat_bind(weapon, PRESET, "golden_slide");

    // Износ на две трети: 21 шаг из 32, на все материалы этого ствола.
    ncl_mat_param_all(weapon, "uWear", 21);
}
```

## 8. Когда ничего не видно

Порядок проверки от дешёвого к дорогому:

1. `r_studio_shader` у клиента равен 1.
2. Версия клиента 2.6.0 или новее.
3. Файл пресета доехал: он должен лежать у клиента по тому же пути, который передан в
   `ncl_mat_bind`.
4. Имя материала есть в файле, а имя текстуры в файле совпадает с именем в модели:
   `matgen uv <model.mdl>`.
5. Лог модуля: неверные аргументы нативов пишутся туда.
6. Локально, без сервера, тот же путь проверяется консольными командами клиента:
   `r_mat_presets [файл]`, `r_mat_entities`, `r_mat_bind <сущность> <пресет> <материал>`,
   `r_mat_param <сущность> <имя|текстура/имя> <шаги>`. `r_mat_bind` без аргументов
   перечисляет привязки и помечает `(never drawn)` те, чей индекс рендер ни разу не
   спрашивал: это привязка, нацеленная на сущность, которую никто не рисует.

7. `matgen check <файл>` разбирает и пресет тоже, отличая его от документа модели по
   форме файла: печатает материалы, программы, картинки и всё, что отверг бы клиент.
