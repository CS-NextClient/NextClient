# План разработки нового рендера

Цели: перевод конвейера на шейдерную модель (таргет OpenGL 3.3 compatibility),
оптимизация, расширяемые эффекты и API для разработчиков AMXX (загрузка своих
шейдеров, готовые эффекты типа обводки игроков через стены и экранных эффектов).

Ориентир по архитектуре ресурсов: статья
<https://habr.com/ru/articles/1039266/> (идентичность ресурса как пара
(источник, параметры), фиксированный набор параметров, хэндлы, группы времени
жизни, журнал описаний загрузки для пересоздания).

Статус (2026-07-09): выполнен аудит ветки feature/advanced-radar на предмет
переиспользуемого кода и подготовительное обобщение по
docs/archive/radar-gl-generalization-tasks.md (коммиты 0f99d99, c55d807, 31d97ae,
d29ab65: пакет ncl_gl, перенос SegPointDistSq в ncl_math, нейтральные
view-глобалы). Разделы ниже учитывают это состояние.
Обновление (2026-07-22): capture-харнесс (radar_dump/radar_shot/tools/radar_tests)
восстановлен непосредственно на feature/advanced-radar (коммит 14927e8), поэтому
упоминания ниже про его cherry-pick из отдельной ветки более неактуальны.

## 1. Текущее состояние (исходная точка)

- Рендер принадлежит стоковому hw.dll (fixed-function GL 1.x). engine_mini уже
  перехватывает все стадии кадра в
  `nextclient/engine_mini/src/graphics/gl_rmain.cpp` (R_Clear, R_SetupGL,
  R_DrawWorld, R_DrawViewModel, R_PolyBlend и т.д.) и чейнит в оригинал. Это
  готовые точки для поэтапной подмены стадий.
- Контекст GL создаётся движком через SDL; NextClient получает пост-хук
  GL_SetMode (`gl_vidnt.cpp`). Радарный код в client_mini уже работает с GL2+
  на этом же контексте, с фоллбэком на классический путь.
- glad уже интегрирован в дерево: `dep/glad` (0.1.36, профиль GL 3.1
  compatibility, включая KHR_debug / ARB_debug_output /
  ARB_framebuffer_object), подключён и к client_mini, и к engine_mini.
  Для таргета плана достаточно перегенерировать под 3.3 compatibility
  (drop-in замена glad.h/glad.c, существующий код компилируется без правок).
- Пакет `nextclient/packages/ncl_gl` (создан подготовительным обобщением):
  - `loader.h`: `ncl_gl::LoadProc` (WGL-загрузчик с фоллбэком на
    opengl32.dll), `EnsureLoaded()` (ленивая одноразовая инициализация glad),
    `IsLoaded()` (запрос без побочной загрузки);
  - `program.h`: `ncl_gl::Program` (enum-индексированная таблица uniform),
    `CompileShader` / `LinkProgram` / `LoadProgram` с возвратом InfoLog через
    out-параметр (ошибки компиляции шейдеров больше не глотаются) и с
    дисциплиной glBindAttribLocation до линковки (атрибут 0 обязан быть
    массивом на compatibility-профиле).
  Потребитель пока один - радар; новый рендер строится поверх этого пакета.
- Менеджер текстур уже существует и близок к идеям статьи:
  `nextclient/engine_mini/src/resource/texture_manager/TextureManager.h` -
  слоты с generation-хэндлами, дедупликация по идентификатору, времена жизни
  Persistent/Session, LRU-вытеснение, состояние Cached. Это работающий образец
  паттерна, который нужно обобщить, а не заменить.
- `nextclient/packages/ncl_math` - математическая база для нового кода:
  типы-значения c layout-гарантиями (zero-copy `Ref()` поверх движковых
  float*, `ColorF::data()` напрямую в glUniform4fv), хелперы движковой
  конвенции (AngleVectors и др.). Для рендера предстоит дописать mat4,
  кватернионы, projection-билдеры, Plane/Frustum, Aabb3 в тех же конвенциях.
  Ловушка: VectorMA_2 намеренно инвертирует Z (задокументировано в коде),
  как общий multiply-add не использовать.
- Главная камера кадра доступна в client_mini: `g_MainViewOrigin` /
  `g_MainViewAngles` (`src/view.cpp`, запись в конце V_CalcRefdef с защитой
  `nextView == 0` от перезаписи picture-in-picture проходами спектатора).
- Механизм доставки встроенных шейдеров проверен: cmrc (CMakeRC) вшивает
  исходники в DLL (`client_mini/CMakeLists.txt`), порт cmakerc в
  vcpkg-манифесте. Ресурсная библиотека у cmrc per-target: у engine_mini
  будет своя.
- Регрессионный инструментарий: radar_shot (полнокадровый захват с чтением из
  GL_DRAW_FRAMEBUFFER_BINDING) + radar_dump + tools/radar_tests
  (imgdiff.py c допусками, radar_harness.py) уже в дереве на
  feature/advanced-radar (коммит 14927e8) и подлежит обобщению в
  A/B-харнесс рендера. Паттерн юнит-тестов без движка
  (компиляция исходников напрямую в gtest-таргет) уже в дереве:
  `client_mini/tests/` (RadarView, NclMath).

## 2. Стэш becf0308 (stash@{10} "On main: render", декабрь 2024)

Ранний proof-of-concept. Переиспользовать выборочно, целиком не восстанавливать.

Ценное:

- конвертер studio-мешей из strip/fan в индексированные треугольники с
  укладкой в общие вершинные/индексные буферы
  (StudioModelsSharedMemoryResource::ReadModel / SetupMeshResource);
- идея GpuBuffer + GpuBufferSlice.

Не переносить:

- интеграция glad - уже в дереве (см. раздел 1), в стэше устаревшая копия;
- ResourceManager из стэша - заглушка (список weak_ptr без ключей
  идентичности, кэша и жизненного цикла);
- Material / Shader / RenderPipeline / RenderObjectBatch - пустые скелеты.

Урок стэша: абстракции строились без потребителя и остались пустыми. План
ниже построен от вертикальных срезов: каждая абстракция появляется под
конкретную задачу.

## 3. Ключевые решения

1. Таргет: GL 3.3 compatibility profile, не core и не 3.1. Оборудование с 3.1
   практически всегда поддерживает 3.3, поэтому 3.1 не расширяет охват.
   Core-профиль исключён: пока хоть одна стадия кадра исполняется стоковым
   hw.dll (fixed-function), старый и новый конвейеры обязаны сосуществовать в
   одном контексте. Полный переход на core возможен только после подмены
   последней стадии; целесообразность оценивается в конце.
2. Инкрементальная подмена стадий, а не параллельный рендер. Уже перехваченные
   R_* стадии подменяются по одной, каждая за cvar-переключателем с фоллбэком
   на оригинал. Образец двухуровневого включения - радар
   (`RadarConfig.cpp`): Active = cvar (намерение пользователя) AND capability
   (фактическая возможность контекста). Продукт остаётся выпускаемым на всём
   протяжении работ.
3. Единый доступ к GL для нового кода: glad через пакет ncl_gl - реализовано
   (см. раздел 1), радар уже переведён. qgl-таблица остаётся только для
   легаси-кода engine_mini.
4. Ресурсная система - обобщение TextureManager, а не новая универсальная
   библиотека. Из статьи берутся: идентичность как пара (источник, параметры)
   с фиксированным набором параметров; типизированные хэндлы
   (индекс + generation); группы времени жизни; журнал описаний загрузки для
   пересоздания после сброса устройства. Внедряется по мере появления
   потребителей, начиная с шейдеров. Конкретное свидетельство в пользу
   "параметры в ключе идентичности": радару пришлось вручную навешивать
   GL_CLAMP_TO_EDGE на чужие текстуры и отслеживать их пересоздание движком
   (артефакт швов тайлов оверью) - владение объектами и параметры в ключе
   снимают весь класс проблем.

## 4. Фазы

### Фаза 0 - фундамент (небольшая)

- Перегенерировать dep/glad под 3.3 compatibility (сейчас 3.1; нужные для
  диагностики расширения уже включены в текущую генерацию).
- Флаг "новый рендер доступен": проверка фактической версии контекста с
  диагностикой в консоль. Образец ленивой проверки - EnsureGlad/Available в
  радаре, обобщить с GL 2.0 на 3.3.
- KHR_debug / ARB_debug_output за cvar с выводом в консоль.
- Tracy GPU-зоны.
- Жизненный цикл GL-объектов: единая точка "устройство сброшено, пересоздать
  всё" (журнал описаний загрузки из статьи).
  Уточнение по факту (2026-08-02): команды `vid_restart` в этом движке нет, а
  контекст создаётся один раз за процесс (`GL_SetMode` из `sys_dll2` на старте).
  Смена разрешения через `_setvideomode` только меняет размер окна
  (`SDL_SetWindowSize`), контекст и имена GL-объектов при этом сохраняются, а
  `_restart` в NextClient перезапускает процесс целиком. Поэтому реально нужны
  две вещи, а не одна: запрет на GL-вызовы после разрушения контекста
  (`Draw_Shutdown`) и пересоздание ресурсов, зависящих от размера фреймбуфера,
  при изменении размера окна. Второе сейчас каждый потребитель делает сам из
  VidInit (образец - радар).
  Рабочий минимальный образец - протокол RadarShader_ResetGl (сброс хэндлов из
  VidInit + ленивое пересоздание). Журнал обязан закрыть две известные дыры
  этого образца: glad-указатели никогда не перезагружаются, а удаление
  хэндлов, созданных в возможно умершем контексте, способно затронуть чужие
  объекты нового контекста.

Критерий выхода: на карте выводится тестовый шейдерный full-screen quad за
cvar, переживающий смену видеорежима.

### Фаза 1 - ресурсный слой, минимально достаточный

- ShaderManager поверх ncl_gl::LoadProgram (компиляция/линковка и вывод ошибок
  уже есть): ключ = (путь к источнику, набор define, таблица uniform-имён), кэш
  программ, hot-reload по cvar. Доставка встроенных шейдеров - cmrc; для
  hot-reload dev-режим чтения с диска поверх cmrc (вшитые ресурсы не
  перезагружаются).
- Сборка программ на старте, а не при первой отрисовке: компиляция GLSL занимает
  достаточно, чтобы читаться как зависание посреди игры, а на старте это время
  уже тратится. Собирается встроенная программа плюс каждая поставляемая пара
  `<имя>.vert` + `<имя>.frag`, у которой есть манифест `<имя>.json`: только такую
  программу может назвать материал, поэтому отладочная пара test_quad в набор не
  входит. Ключ `-noshaderwarmup` в командной строке отключает стартовую сборку
  целиком; это запасной выход для драйвера, чей компилятор GLSL её не переживает
  (cvar на этот момент ещё не существуют).
- Между запусками программы хранятся в виде блобов, которые выдал сам драйвер
  (`GL_ARB_get_program_binary`), в `<gamedir>/cache/shaders.bin`. Файл целиком
  привязан к паре «драйвер + GPU» (`GL_VENDOR/RENDERER/VERSION/GLSL`), запись
  ключуется хэшем исходников после подстановки define; блоб, который драйвер
  отверг, молча заменяется компиляцией. Cvar для отключения кэша нет намеренно:
  разогрев идёт из хука `GL_SetMode`, то есть до `Draw_Init` и тем более до
  исполнения `config.cfg`, поэтому переключатель вёл бы себя по-разному в
  зависимости от момента чтения. Сбросить кэш можно `r_reload_shaders` или
  удалением файла. Смена значения `r_shader_reload` (в том числе из config.cfg
  при старте) сама сбрасывает и пересобирает набор через хук cvar, так что
  сессия с чтением шейдеров с диска не требует ручной команды.
- При `developer 1` пишется строка на программу: откуда она взялась (кэш или
  компиляция), размеры исходников и блоба, время. Драйверный info log забирается
  и при успешной сборке, а не только при ошибке, поэтому предупреждение о
  конструкции, которую драйвер читает по-своему, видно до того, как оно
  превратится в отчёт с одной машины. Стартовые строки требуют `-dev` в командной
  строке: разогрев идёт до `config.cfg`, так что заданный там `developer` ещё не
  применён. Тот же вывод после `developer 1` в консоли даёт `r_reload_shaders`,
  который теперь пересобирает набор сразу, а не оставляет каждую программу до её
  следующей отрисовки.
- GpuBufferManager по мотивам стэша: сначала простые статические буферы и
  слайсы, без преждевременной субаллокации.
- TextureManager: добавить параметры загрузки в ключ идентичности и
  пересоздание после сброса устройства.

Критерий выхода: все GPU-ресурсы создаются только через менеджеры и корректно
пересоздаются при рестарте видео.

### Фаза 2 - первый боевой потребитель: studio-модели

- Перенос studio-рендера на VBO + шейдеры (за cvar), GPU-скиннинг (матрицы
  костей в UBO). Переиспользуется конвертер мешей из стэша; конвертер
  оформить как engine-free модуль с юнит-тестами по образцу
  client_mini/tests (RadarView: чистая математика, компиляция исходника
  напрямую в gtest-таргет).
- Здесь появляются Material (текстура + рендер-режим + флаги) и батчинг - под
  реальные требования chrome, glow shell, render modes. Прецедент формы -
  радарный "collect в POD-массив задач, затем послойные проходы с flush при
  смене состояния" (HudRadarAdvanced/DrawPlayerLayers).
- На границах стадий со старым конвейером сохранять/восстанавливать состояние
  GL; стартовый чек-лист ловушек уже собран радаром (кэш привязки текстур в
  GL_Bind hw.dll, инвалидация blend-кэша при чужих изменениях, save/restore
  GL_ARRAY_BUFFER_BINDING перед клиентскими массивами) - расширить для
  world/studio стадий (матрицы, active texture, depth/cull).
- Верификация: харнесс уже в дереве (radar_dump/radar_shot/tools/radar_tests,
  коммит 14927e8); добавить A/B-режим (два запуска с cvar нового рендера 0/1, диф между
  прогонами вместо машинно-зависимых голденов), захват на нужной границе R_*
  стадии. Для непиксельной верификации - образец radar_dump: армированный
  дамп состояния кадра в диф-дружелюбный JSON (хэши костей, счётчики батчей,
  ключи материалов).

Обоснование выбора: самый заметный выигрыш производительности (CPU-скиннинг и
immediate mode на каждой модели игрока), при этом путь самодостаточен через
уже перехваченные точки.

### Фаза 3 - мир (BSP)

- VBO-геометрия мира, атлас лайтмапов. Компактный рабочий референс обхода
  model_s/msurface_t/glpoly_t (раскладка UV базы и лайтмапа, SURF_PLANEBACK,
  выбор страницы атласа) - `client_mini/src/hud/radar/MapRender.cpp`;
  сам рисующий код оттуда не брать (immediate mode).
- Известная ловушка порядка загрузки: eng()->lightmap_textures невалидны
  первые кадры после загрузки карты - пока лайтмапы строит hw.dll, проверять
  готовность и откладывать (как делает радар); уходит полностью, когда фаза 3
  забирает построение лайтмапов себе.
- Корректный overbright в шейдере (попутно закрывается известная проблема
  gl_overbright на мультитекстурном пути).
- Detail textures, вода, скайбокс, декали.
- PVS/culling мира: в радарном коде доступа к листьям/кластерам BSP нет
  (его видимость чисто трейсовая), источник - worldmodel через engine_mini.
- После этой фазы гамма-конвейер (сейчас разделён между NextClient и hw.dll)
  полностью переходит под контроль клиента.

Самая объёмная фаза.

### Фаза 4 - пост-обработка и API для AMXX

- Каркас: сцена в FBO, стек пост-эффектов, вывод в backbuffer. Ядро захвата
  уже реализовано и проверено в радаре
  (`RadarShader.cpp`, RadarShader_DrawBlurBackground): определение реального
  места рендера через GL_DRAW_FRAMEBUFFER_BINDING (0 = backbuffer, иначе FBO
  при fullscreen/-stretchaspect), 1:1 resolve через glBlitFramebuffer
  (совместимо с MSAA), save/restore READ/DRAW привязок, масштабирование
  HUD-координат в пиксели фреймбуфера. Обобщить, отделив от радарных
  масок/затемнения; правило порядка "захватывающий проход раньше рисующих в
  регион" сделать явным в frame graph, а не конвенцией.
- Дешёвый blur радара (1:1 resolve, downsample 4x, mipgen малой текстуры,
  выборка высокого LOD) - готовый бюджетный tier эффекта; полноэкранный blur
  фазы 4 при необходимости делает separable-проходы. SDF-сниппеты
  аналитического AA из радарных шейдеров пригодны для масок/виньеток.
- API строить как "готовые параметризуемые эффекты + ограниченные
  пользовательские шейдеры", а не произвольный доступ к конвейеру:
  - обводка игроков через стены (ID/stencil-проход по entity; видимость
    сквозь стены - штатное свойство прохода, трейсовая Visibility радара тут
    не нужна);
  - опциональные правила гейтинга эффектов по прямой видимости - на радарном
    рецепте трассировки вне event-пути (EV_SetUpPlayerPrediction +
    Push/PopPMStates, `Visibility.cpp`) и идиоме свежести entity-слотов
    (messagenum);
  - цветокоррекция, виньетка, blur, chromatic aberration;
  - пользовательские фрагментные шейдеры экрана с фиксированным интерфейсом
    uniform-переменных, доставка через штатный механизм прекэша/докачки
    ресурсов, лимиты и валидация при компиляции (тексты ошибок уже
    возвращает ncl_gl);
  - сосуществование с движковыми screenfade/R_PolyBlend: образец чтения
    активного фейда клиентом - радарный LocalBlind.
- Черновик API зафиксировать уже перед фазой 2: требования эффектов (например,
  ID-буфер для обводки) влияют на архитектуру материалов и проходов.
- Таблицу cvar рендера оформить по образцу radar_cvars.h (constexpr-таблица
  {имя, дефолт, min, max} + compile-time проверка потребителей в engine_mini
  и GameUI), заголовок в публичном include engine_mini.

## 5. Первые практические шаги

## 6. Ограничения и риски

- Процесс 32-битный: CPU-копии вершинных данных и атласов освобождать сразу
  после загрузки в VRAM; бюджетирование адресного пространства важнее бюджета
  видеопамяти.
- GL-загрузка и выгрузка только в главном потоке (контекст движка);
  асинхронная загрузка ресурсов, если потребуется, реализуется через очередь
  загрузки в главный поток, без shared-контекстов на старте.
- Пока стадии подменяются частично, состояние GL между старым и новым кодом
  должно аккуратно сохраняться/восстанавливаться на границах стадий
  (см. чек-лист в фазе 2).
- glad-указатели загружаются один раз на процесс; на WGL это работает
  (proc-адреса per-ICD, не per-context), но фаза 0 обязана сделать это
  допущение явным и перезагружать указатели в точке сброса устройства.
- Фоллбэк на классический путь сохраняется за cvar на весь переходный период;
  это удваивает стоимость поддержки затронутых стадий и учитывается при
  планировании объёма фаз.
