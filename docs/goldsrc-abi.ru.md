# Сопровождение объявлений ABI GoldSrc

[English version](goldsrc-abi.md)

`nextclient/goldsrc_abi` содержит объявления для взаимодействия со штатным 32-битным движком GoldSrc и игровой библиотекой Counter-Strike. ABI определяет двоичный интерфейс: размещение данных в памяти и правила вызова функций. Интерфейсная цель CMake `goldsrc::abi` предоставляет заголовки и задает требование C++23. Факты о движке относятся к сборке 8684. Наличие объявления не подтверждает совместимость с другой сборкой.

При изменении библиотеки действуют [правила модуля](../nextclient/goldsrc_abi/AGENTS.md). За определение адресов и регистрацию перехватов отвечает [NitroApi](../nextclient/nitro_api/AGENTS.md).

## С чего начать

Для проверки текущей модели нужен Python 3. Из корня репозитория выполните:

```text
python nextclient/goldsrc_abi/tools/library.py check
```

Команда сообщает о проблемах модели и не перезаписывает заголовки. Для изменения объявлений следуйте разделу [«Добавление или исправление факта»](#добавление-или-исправление-факта), затем [сгенерируйте файлы в отдельный каталог](#генерация) и сравните их с отслеживаемыми файлами.

## Источники и их назначение

| Источник | Назначение |
|---|---|
| [facts.json](../nextclient/goldsrc_abi/tools/facts.json) | Зафиксированные факты совместимости, ревизии источников, инструменты извлечения и результаты самопроверки компилятором |
| [facts_linux.json](../nextclient/goldsrc_abi/tools/facts_linux.json) | Независимо проверенное размещение структур Linux x86 в памяти и источники измерений |
| [header_map.json](../nextclient/goldsrc_abi/tools/header_map.json) | Размещение объявлений в файлах, имена, полнота объявлений, замены и группы констант |
| [library.py](../nextclient/goldsrc_abi/tools/library.py) | Проверка модели и генерация заголовков и проверок размещения данных в памяти |
| [model.py](../nextclient/goldsrc_abi/tools/goldsrc_tools/model.py) | Полный набор зависимостей, порядок объявлений и модель для генерации |
| [platforms.py](../nextclient/goldsrc_abi/tools/goldsrc_tools/platforms.py) | Проверка дополнения и отдельные модели Windows x86 и Linux x86 |
| [emit.py](../nextclient/goldsrc_abi/tools/goldsrc_tools/emit.py) | Формирование текста из модели |
| [golden_layout.cpp](../nextclient/goldsrc_abi/tests/golden_layout.cpp) | Проверки компилятором по записанным фактам |

Генератор читает зафиксированные факты и карту объявлений. Он не выводит факты из кода, который сейчас использует эти объявления. Разделы `sources` и `tools` в JSON определяют исходные данные для извлечения. Пути в ключах фактов входят в идентификаторы этих данных.

Версионируемая схема дополнения Linux и воспроизводимые измерения описаны в [справке об источниках Linux](goldsrc-abi-linux-facts.ru.md). Канонический хеш `base_facts_sha256` связывает дополнение с зафиксированными исходными данными Windows. Для каждой полной структуры или структуры с описанным началом, включая вложенные зависимости, нужны отдельные измерения Linux и успешная независимая проверка компилятором. Генерация блокируется, если измерения отсутствуют, идентификаторы конфликтуют, сведения об источниках устарели или самопроверка завершилась ошибкой. Для неполных структур Linux размещение данных не выводится из предположений. Размещение структур Windows соответствует зафиксированным значениям.

В заголовках также есть дополнения, поддерживаемые вручную. В частности, константы `OBS_*` в [pmove.h](../nextclient/goldsrc_abi/include/goldsrc/pmove.h) не входят в генерируемую модель. Генератор перезаписывает результат и не объединяет его с такими дополнениями. Перед заменой файлов нужно сравнить результат с текущими заголовками и явно сохранить каждое проверенное дополнение. Проверка модели сама по себе не проверяет эти дополнения.

[Факты Studio](../nextclient/goldsrc_abi/tools/maintained_studio_facts.json) содержат хеши источников, константы, размеры, выравнивание и смещения полей объявлений, поддерживаемых вручную. Генератор не читает этот файл. [Проверки размещения структур Studio](../nextclient/goldsrc_abi/tests/studio_layout.cpp) проверяют объявления при компиляции цели `goldsrc_abi_golden`. Команды с локальными путями и результаты запусков хранятся в игнорируемых отчетах сессии или сборки.

## Правила объявлений

- `goldsrc` содержит факты штатного движка, `goldsrc::cstrike` содержит факты
  штатной библиотеки Counter-Strike. Расширения NextClient относятся к своему
  модулю и не должны добавлять поля в штатные структуры.
- Сохраняются штатные имена типов, полей, элементов таблиц функций и констант.
  Это общие имена, по которым взаимодействуют компоненты. Если у штатного типа
  есть псевдонимы, имя объявления определяется картой.
- В заголовках и исходниках штатные имена указываются с пространством имен.
  Директива `using namespace goldsrc` не допускается. Если тип используется
  только через указатель, подключается `<goldsrc/fwd.h>`. Штатные теги типов
  и typedef не объявляются повторно в коде, который их использует.
- Объявляются только нужные типы и их зависимости. Связанные наборы
  идентификаторов, например оружия или сообщений протокола, сохраняются целиком.
- Сохраняются возвращаемые типы, число уровней указателей, соглашения о вызовах,
  порядок элементов таблиц, упаковка, смещения полей и базовые типы перечислений.
  Сходство типов C++ не подтверждает совместимость ABI.
- Поля штатных структур не получают инициализаторов по умолчанию. Для
  целочисленных псевдонимов, заменяемых по карте, используются типы `<cstdint>`.
  Имена, принятые в сигнатурах, например `qboolean`, `vec3_t` и `CRC32_t`, сохраняются.
- Константы объявляются как типизированные `inline constexpr`, перечисления
  сохраняют штатную форму. Карта задает десятичную или шестнадцатеричную запись
  для каждой группы констант.

## Полнота описания структур

Карта определяет три формы объявлений:

| Форма | Применение и обязательные свойства |
|---|---|
| Полная | Публичные структуры, таблицы функций и структуры, вложенные по значению, полностью описывают нужные поля. |
| Неполная | Для внутреннего типа, используемого только через указатели, достаточно предварительного объявления. |
| Описанное начало и неописанный остаток | Внутренняя структура открывает нужные начальные поля и резервирует память под остальные штатные данные. |

Структура с описанным началом сохраняет штатные `sizeof` и `alignof`, включая наследование и промежутки для выравнивания. Поле `unmodelled_` занимает штатную память после описанного начала и не расширяет структуру. Генерируемое объявление использует записанное выравнивание. Если последнее нужное поле битовое или безымянное, описание продолжается до именованного небитового поля перед остатком. Структура без описанных полей также резервирует нужную память после базовых классов.

Полный размер нужен даже при чтении только начальных полей: от него зависят индексация массивов, арифметика указателей, выделение, очистка и копирование памяти, а также запись данных движком. Все затронутые смещения и размещение структуры целиком проверяются для x86. Успешная проверка Python на машине разработчика не подтверждает 32-битное размещение структур C++.

## Добавление или исправление факта

1. Определить, для чего нужен факт и какому бинарному файлу он принадлежит.
   Адреса конкретных сборок относятся к NitroApi; тип NextClient остается в
   своем модуле.
2. Получить спецификацию интерфейса из мест вызова в проекте, анализа
   поставляемого бинарного файла движка, публичной документации или отдельно
   извлеченных фактов. Записать ревизию источника или сборку, версии инструментов,
   имена и типы полей, смещения, сигнатуры, значения и существенные особенности
   их использования.
3. Разделять извлечение фактов и реализацию. Автор замены работает по
   спецификации или JSON с фактами, не открывая при написании оригиналы Valve,
   утечки или GPL-код. Такой подход называется clean-room-разработкой.
   Не копировать реализацию, комментарии, заголовочные уведомления, оформление
   и произвольную организацию файлов. Не выводить замены из GPL-исходников Quake
   или Xash3D. Для нового поведения нужна отдельная спецификация.
4. Принимать извлеченные данные только после устранения всех обнаруженных
   проблем, включая неполноту данных и ошибки самопроверки компилятором.
   Сохранять явно названные исключения и их основания. Не считать неизмеренные
   значения подтвержденными.
5. При изменении генерируемой модели одновременно обновлять факты, карту,
   объявления и ожидаемое размещение данных в памяти. Дополнения, поддерживаемые
   вручную, проверять отдельно; при их изменении добавлять соответствующие проверки.
6. Записать, какие факты описывает каждая замена и как они получены, в сведениях
   о происхождении изменения и сообщении коммита. Не помещать сведения об
   источниках в комментарии к коду.

Объявления с признаком `moved_hltv_interface` относятся к сохраняемым интерфейсам форка и не используются как исходные данные clean-room-разработки новых заголовков. Шесть интерфейсов перечислены в [abi_scope.py](../nextclient/goldsrc_abi/tools/goldsrc_tools/abi_scope.py). Диагностика миграции может цитировать фрагменты этих файлов. Такие журналы не используются при реализации и не открываются при clean-room-разработке.

## Генерация

Команды выполняются из корня репозитория:

```text
python nextclient/goldsrc_abi/tools/library.py check
python -m unittest discover -s nextclient/goldsrc_abi/tools -t nextclient/goldsrc_abi/tools -p "test_*.py"
python nextclient/goldsrc_abi/tools/library.py headers --out build/abi-review/include
python nextclient/goldsrc_abi/tools/library.py tests --out build/abi-review/tests
```

Если Python вызывается командой `python3`, нужно использовать ее. Команды генерации принимают параметры `--facts`, `--linux-facts`, `--map` и `--clang-format`. Дополнение Linux по умолчанию находится в `tools/facts_linux.json`. Одни и те же команды генерируют файлы из обеих платформенных моделей. Общие объявления выводятся один раз, различающиеся объявления и проверки разделяются ветвями для соответствующих платформ. Заголовок предварительных объявлений отклоняет неподдерживаемые платформы и требует четырехбайтовых указателей. По умолчанию команды записывают результат в отслеживаемые Git каталоги заголовков и тестов, поэтому для сравнения нужно явно задать отдельный каталог. Команда `headers` также удаляет из своего выходного каталога `goldsrc/` файлы `.h`, отсутствующие в модели.

Каталог сравнения должен находиться внутри репозитория, чтобы clang-format нашел корневую конфигурацию. Результат форматирования зависит и от версии clang-format, которую генератор выводит в журнал. Нужно сравнить наборы файлов и их содержимое, сохранить поддерживаемые дополнения и проверить diff перед заменой файлов.

Проверки размещения данных в памяти компилируются в настроенной сборке x86, например:

```text
cmake --build --preset vs2022-release --target goldsrc_abi_golden
```

`goldsrc_abi_golden` является объектной целью с проверками компилятора, а не исполняемым тестом. Нужно собрать NitroApi и затронутые компоненты, использующие объявления, в соответствующих конфигурациях. Изменение публичного API также требует проверки экспортов, смещений полей, сигнатур и применимых поставщиков адресов. Проверки в работающей игре учитываются отдельно; игру запускает разработчик.

## Зафиксированные пути извлечения

`facts.py`, `usage.py` и `codemod.py` используют зафиксированную модель извлечения. Пути вида `dep/NclNitroApi` и `dep/NclNitroApi/dep/ncl-hl1-source-sdk` обозначают дерево исходников, из которого получены факты. Текущие компоненты, использующие объявления, и расположение их файлов не заменяют эти исходные данные.

`abi_scope.EXTRACTION_SDK_DIR`, `OUR_SOURCE_DIRS`, `NITROAPI_DIR`, сведения о репозиториях в `facts.py` и классификация путей в `migration.py` меняются только вместе, в рамках явно определенной миграции исходных данных. Отдельные зафиксированные пути не обновляются. У `abi_scope.SDK_DIR` другая роль: он задает текущий путь форка SDK для проверки происхождения зависимостей.

Для повторного извлечения нужно использовать дерево, соответствующее записанным исходным данным, и сохранить сведения о его происхождении. `facts.py` требует `--out`; результатом извлечения из текущего дерева нельзя перезаписывать зафиксированные факты. При замене исходных данных проверяются изменения содержимого записей, а не только наборы ключей. Одноименные макросы из разных источников проверяются повторно.

## Проверка происхождения зависимостей

Полная последовательность задана в [workflow сборки](../.github/workflows/build.yml). Запрос CMake File API `codemodel-v2` создается до конфигурации. Проверка запускается после сборки, когда сгенерированные исходники ресурсов уже существуют:

```text
python nextclient/goldsrc_abi/tools/provenance.py --build-dir build/vs2022 --config Release --allowlist .github/provenance-allowlist.json --report build/provenance-report.json
```

Для каждой бинарной цели отчет прослеживает включения файлов через директивы include и зависимости от статических и объектных библиотек при линковке. Зависимости, задающие только порядок сборки, учитываются отдельно. Инструмент проверяет уведомления в исходниках и состав зависимостей. Он не определяет, какие функции остаются после линковки, и не дает правового заключения о бинарном файле.

Список разрешений фиксирует допустимый набор файлов и зависимостей, а также исключенные зависимости. Его не следует расширять для допуска новой зависимости. `--update-allowlist` удаляет устаревшие записи; изменения классификации зависимостей нужно проверять явно. Если настроенная цель заявлена свободной от отмеченных источников, новые отмеченные источники не должны попадать в ее зависимости.

После удаления исходников или изменения графа сборки нужно повторить конфигурацию. Снимки зависимостей сравниваются только для объектов текущего графа; устаревшие записи журнала Ninja не относятся к текущим зависимостям. Для нового проверочного скрипта нужны проверенный пример, на котором он обнаруживает ошибку, и непустой набор проверяемых объектов. Вместе с результатами сохраняются дерево сборки, цель, конфигурация и полный вывод.

## Интеграция с NitroApi

Для функции, доступной через API, нужны публичное объявление, `StaticHookId`, регистрация модуля и записи поддерживаемых поставщиков адресов. Для переменной нужны объявление, `RegisterVar` и данные поставщика. Существующие смещения публичных полей и значения идентификаторов перехватов сохраняются. Новые поля добавляются в конец; неявное увеличение значений enum проверяется отдельно.

Поставщики адресов Windows и Linux проверяются отдельно. Адаптеры перехватов сохраняют исходное соглашение о вызовах, правила передачи управления по цепочке и возврата результата. Компиляция не подтверждает совпадение адресов в работающем процессе.

`GameHud.h` предварительно объявляет `class Vector`. Код, которому нужно определение, самостоятельно подключает `<mathlib/vector.h>`. Подключение этого файла в публичном заголовке добавляет динамическую инициализацию и зависимость от tier0 при линковке в Debug. Отдельная копия `easyloggingpp` в NitroApi также имеет собственное поведение; при изменении объявлений ABI ее нельзя объединять с другой копией.
