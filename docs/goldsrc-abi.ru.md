# Сопровождение деклараций GoldSrc ABI

[English version](goldsrc-abi.md)

`nextclient/goldsrc_abi` содержит декларации для взаимодействия со штатным
32-битным движком GoldSrc и игровой библиотекой Counter-Strike. Интерфейсная цель
CMake `goldsrc::abi` предоставляет заголовки и требование C++23. Факты о движке
относятся к сборке 8684. Наличие декларации не подтверждает совместимость с другой
сборкой.

При изменении библиотеки действуют [правила модуля](../nextclient/goldsrc_abi/AGENTS.md).
За разрешение адресов и регистрацию перехватов отвечает
[NitroApi](../nextclient/nitro_api/AGENTS.md).

## Источники и ответственность

| Источник | Назначение |
|---|---|
| [facts.json](../nextclient/goldsrc_abi/tools/facts.json) | Закрепленные факты совместимости, ревизии источников, средства извлечения и результаты самопроверки компилятором |
| [header_map.json](../nextclient/goldsrc_abi/tools/header_map.json) | Размещение, имена, полнота деклараций, замены и группы констант |
| [library.py](../nextclient/goldsrc_abi/tools/library.py) | Проверка модели и генерация заголовков и проверок размещения в памяти |
| [model.py](../nextclient/goldsrc_abi/tools/goldsrc_tools/model.py) | Зависимости, порядок деклараций и модель для генерации |
| [emit.py](../nextclient/goldsrc_abi/tools/goldsrc_tools/emit.py) | Формирование текста из модели |
| [golden_layout.cpp](../nextclient/goldsrc_abi/tests/golden_layout.cpp) | Проверки компилятором по записанным фактам |

Генератор читает закрепленные факты и карту. Он не восстанавливает факты по текущим
потребителям. Разделы `sources` и `tools` в JSON определяют входные данные
извлечения; пути в ключах фактов входят в идентификацию этих данных.

В заголовках также есть дополнения, поддерживаемые вручную. В частности, константы
`OBS_*` в [pmove.h](../nextclient/goldsrc_abi/include/goldsrc/pmove.h) не входят в
генерируемую модель. Генератор перезаписывает результат и не объединяет его с
такими дополнениями. Перед заменой файлов следует сравнить результат с текущими
заголовками и явно сохранить каждое проверенное дополнение. Проверка модели сама
по себе не проверяет эти дополнения.

## Правила деклараций

- `goldsrc` содержит факты штатного движка, `goldsrc::cstrike` содержит факты
  штатной библиотеки Counter-Strike. Расширения NextClient принадлежат своему
  модулю и не должны добавлять поля в штатные структуры.
- Сохраняются штатные имена типов, полей, элементов таблиц функций и констант.
  Они составляют общий словарь интерфейса. При наличии псевдонимов имя декларации
  определяется картой.
- Штатные имена указываются с пространством имен в заголовках и исходных файлах.
  Директива `using namespace goldsrc` не допускается. Для объявлений через
  указатель используется `<goldsrc/fwd.h>`, без повторного объявления штатных
  тегов или typedef в потребителе.
- Описываются нужные типы и их зависимости. Связанные наборы идентификаторов,
  например оружие или сообщения протокола, сохраняются целиком.
- Сохраняются возвращаемые типы, глубина указателей, соглашения о вызовах, порядок
  элементов таблиц, упаковка, смещения полей и базовые типы перечислений. Сходство
  типов C++ не подтверждает совместимость ABI.
- Поля штатных структур не получают инициализаторов по умолчанию. Для заменяемых
  картой целочисленных псевдонимов используются типы `<cstdint>`; имена из словаря
  сигнатур, например `qboolean`, `vec3_t` и `CRC32_t`, сохраняются.
- Константы объявляются как типизированные `inline constexpr`, перечисления
  сохраняют штатную форму. Десятичное или шестнадцатеричное представление каждой
  группы констант задается картой.

## Полнота размещения в памяти

Карта определяет три формы деклараций:

| Форма | Применение и обязательные свойства |
|---|---|
| Полная | Публичные структуры, таблицы функций и структуры, вложенные по значению, описывают требуемые поля полностью. |
| Неполная | Внутренний тип, используемый только через указатель, может оставаться предварительным объявлением. |
| Префикс с непрозрачным остатком | Внутренняя структура с обращениями к полям описывает нужный префикс и резервирует остальные штатные байты. |

Структура с префиксом сохраняет штатные `sizeof` и `alignof`, включая наследование
и выравнивающие промежутки. `unmodelled_` занимает штатную память после описанного
префикса и не является расширением. Генерируемая декларация использует записанное
выравнивание. Если последнее нужное поле битовое или безымянное, префикс
продолжается до именованного небитового поля перед остатком. Структура без
описанных полей также резервирует нужную память после базовых классов.

Полный размер необходим даже при чтении только начальных полей: от него зависят
индексация массивов, арифметика указателей, выделение, очистка и копирование памяти,
а также запись движка. Смещения и итоговое размещение проверяются для цели x86.
Успешная проверка Python на машине разработчика не подтверждает 32-битное
размещение C++.

## Добавление или исправление факта

1. Определить потребность потребителя и библиотеку, которой принадлежит факт.
   Адреса для конкретных сборок относятся к NitroApi, тип NextClient остается в
   своем модуле.
2. Получить спецификацию интерфейса из мест вызова проекта, анализа поставляемого
   двоичного файла, публичной документации или отдельно извлеченных фактов.
   Записать ревизию источника или сборку, версии инструментов, имена и типы полей,
   смещения, сигнатуры, значения и существенную семантику.
3. Разделять извлечение и реализацию. Автор замены работает по спецификации или
   JSON фактов, не открывая при написании оригиналы Valve, утечки или GPL-код.
   Не копировать реализацию, комментарии, заголовочные уведомления, оформление и
   произвольную организацию файлов. Не выводить замены из GPL-исходников Quake
   или Xash3D. Новому поведению требуется отдельная спецификация поведения.
4. Принимать извлеченные данные после устранения всех обнаруженных проблем,
   включая ошибки полноты и самопроверки компилятором. Сохранять явно названные
   исключения и их основания. Не считать неизмеренные значения подтвержденными.
5. Для изменения генерируемой модели одновременно обновлять факты, карту,
   декларации и ожидаемое размещение. Дополнения, поддерживаемые вручную,
   проверять отдельно; при их изменении добавлять соответствующие проверки.
6. Зафиксировать, какие факты описывает каждая замена и как они получены, в записи
   о происхождении изменения и сообщении коммита. Не помещать сведения о
   происхождении в комментарии исходного кода.

Декларации с признаком `moved_hltv_interface` относятся к сохраняемым интерфейсам
форка и не служат входом clean-room для новых заголовков. Шесть интерфейсов
перечислены в [abi_scope.py](../nextclient/goldsrc_abi/tools/goldsrc_tools/abi_scope.py).
Диагностика миграции может цитировать фрагменты этих файлов. Такие журналы не
используются при реализации и не открываются в контексте clean-room-разработки.

## Генерация

Команды выполняются из корня репозитория:

```text
python nextclient/goldsrc_abi/tools/library.py check
python -m unittest discover -s nextclient/goldsrc_abi/tools -t nextclient/goldsrc_abi/tools -p "test_*.py"
python nextclient/goldsrc_abi/tools/library.py headers --out build/abi-review/include
python nextclient/goldsrc_abi/tools/library.py tests --out build/abi-review/tests
```

Если Python вызывается командой `python3`, следует использовать ее. Команды
генерации принимают параметры `--facts`, `--map` и `--clang-format`. По умолчанию
они записывают результат в отслеживаемые каталоги заголовков и тестов, поэтому для
сравнения явно задается отдельный каталог. Команда `headers` также удаляет из
своего выходного каталога `goldsrc/` файлы `.h`, отсутствующие в модели.

Каталог сравнения должен находиться внутри репозитория, чтобы clang-format нашел
корневую конфигурацию. Результат зависит и от версии clang-format, которую
генератор выводит в журнал. Следует сравнить наборы файлов и содержимое,
сохранить поддерживаемые дополнения и проверить diff перед заменой файлов.

Проверки размещения компилируются в настроенной сборке x86, например:

```text
cmake --build --preset vs2022-release --target goldsrc_abi_golden
```

`goldsrc_abi_golden` является объектной целью с проверками компилятора, а не
исполняемым тестом. Нужно собрать NitroApi и затронутых потребителей в нужных
конфигурациях. Изменение публичного API также требует проверки экспортов,
смещений членов, сигнатур и применимых поставщиков адресов. Проверки в работающей
игре учитываются отдельно; игру запускает разработчик.

## Закрепленные пути извлечения

`facts.py`, `usage.py` и `codemod.py` используют закрепленную модель извлечения.
Пути вида `dep/NclNitroApi` и `dep/NclNitroApi/dep/ncl-hl1-source-sdk` обозначают
дерево источников, из которого получены факты. Текущие потребители деклараций и
координаты файлов не являются эквивалентными входными данными.

`abi_scope.EXTRACTION_SDK_DIR`, `OUR_SOURCE_DIRS`, `NITROAPI_DIR`, сведения о
репозиториях в `facts.py` и классификация путей в `migration.py` изменяются только
в рамках согласованной миграции входных данных. Отдельные закрепленные пути не
обновляются. У `abi_scope.SDK_DIR` другая роль: он определяет текущий путь форка
SDK для проверки происхождения зависимостей.

Повторное извлечение выполняется на дереве, соответствующем записанным входным
данным, с сохранением происхождения. `facts.py` требует `--out`; результатом
извлечения из текущего дерева нельзя перезаписывать закрепленные факты. При
замене исходных данных сравнивается содержимое записей, а не только наборы ключей,
и повторно проверяются одноименные макросы из разных источников.

## Проверка происхождения зависимостей

Полная последовательность задана в [workflow сборки](../.github/workflows/build.yml).
Запрос CMake File API `codemodel-v2` создается до конфигурации. Проверка запускается
после сборки, когда сгенерированные исходники ресурсов уже существуют:

```text
python nextclient/goldsrc_abi/tools/provenance.py --build-dir build/vs2022 --config Release --allowlist .github/provenance-allowlist.json --report build/provenance-report.json
```

Для каждой двоичной цели отчет учитывает текстовые включения и связанные с ней
статические и объектные библиотеки. Зависимости, задающие только порядок сборки,
учитываются отдельно. Инструмент проверяет уведомления в исходниках и состав
зависимостей; он не определяет, какие функции сохраняются после линковки, и не
дает правового заключения о двоичном файле.

Список разрешений фиксирует допустимые файлы и исключенные зависимости. Его не
следует расширять для допуска новой зависимости. `--update-allowlist` удаляет
устаревшие записи; изменения классификации зависимостей проверяются явно.
Цель, заявленная свободной от отмеченных источников, должна сохранять это свойство.

После удаления исходников или изменения графа сборки требуется новая
конфигурация. Снимки зависимостей сравниваются только для объектов текущего графа;
устаревшие записи журнала Ninja не относятся к текущим зависимостям. Новому
проверочному скрипту нужны проверенный отрицательный пример и непустой набор
проверяемых объектов. В результатах сохраняются дерево сборки, цель,
конфигурация и полный вывод.

## Интеграция с NitroApi

Для доступной через API функции необходимы публичная декларация, `StaticHookId`,
регистрация модуля и записи поддерживаемых поставщиков адресов. Для переменной
необходимы декларация, `RegisterVar` и данные поставщика. Существующие смещения
публичных членов и значения идентификаторов перехватов сохраняются. Новые члены
добавляются в текущий конец; неявное увеличение значений enum проверяется отдельно.

Поставщики адресов Windows и Linux требуют отдельных проверок. Адаптеры
перехватов сохраняют исходное соглашение о вызовах, порядок передачи управления
по цепочке и возвращаемое значение. Компиляция не подтверждает совпадение адресов
в работающем процессе.

`GameHud.h` предварительно объявляет `class Vector`. Потребители, которым нужно
определение, самостоятельно включают `<mathlib/vector.h>`. Включение этого файла
в публичный заголовок добавляет динамическую инициализацию и зависимость от tier0
при линковке потребителей в Debug. Частная копия `easyloggingpp` в NitroApi также
имеет собственное поведение; ее объединение с другой копией не входит в изменение
деклараций ABI.
