# Проверка установки и фабрики поставляемого провайдера

[English version](installation-and-factory.md) | [Указатель проверок](README.ru.md)

Выполняйте проверки из корня репозитория в окружении сборки x86. Перед сборкой настройте поддерживаемый пресет. Команды ниже используют отслеживаемые пресеты Ninja Multi-Config. Собирайте по одной цели за команду и указывайте конфигурацию. Проверки используют подготовленные файлы и временные каталоги назначения внутри каталога сборки. Игра и сервер для них не требуются.

## Проверка ресурсов перед установкой

`BUILD_ALL` вызывает `cmake/InstallNextClient.cmake` с созданным манифестом `build/<preset>/install-nextclient-<config>.cmake`, который содержит только данные. Скрипт проверяет каждый файл в `assets/cstrike/materials` на содержимое указателя Git LFS до создания каталогов, копирования файлов и резервного копирования Linux VGUI. Затем он устанавливает восемь поставляемых модулей, файлы соответствующей платформы, ресурсы и согласованную библиотеку Tracy при включенном профилировании. В Linux существующая резервная копия `vgui2.so.valve` сохраняется.

Настройте тестовую сборку и соберите цель проверки фабрики перед запуском зарегистрированных проверок установки и фабрики:

```powershell
cmake --preset ninja-tests
cmake --build --preset ninja-tests-release --target verify-nitro-api-factory
ctest --test-dir build/ninja-tests -C Release -R '^(installation-preflight|nitro-api-shipping-factory.*)$' --output-on-failure
```

`installation-preflight` выполняет рабочий скрипт установки для Windows и Linux с включенным и выключенным профилированием. Фикстуры содержат различные данные библиотек и ресурсов, вложенный материал с указателем LFS, контрольные файлы назначения и пути с пробелами. Отказ должен сохранить полный список файлов и каталогов назначения вместе с SHA-256, не создать резервную копию Linux VGUI и не создать отсутствующий каталог назначения. После замены указателя обычными данными должны установиться ожидаемые модули, ресурсы и необязательная библиотека Tracy. Повторная установка Linux должна сохранить исходную резервную копию. Тест пересоздает только `<binaryDir>/install-nextclient-fixtures`, предварительно разрешив его путь и проверив, что он остается внутри выбранного каталога сборки CMake.

Эта проверка подтверждает порядок предварительной проверки и соответствие путей для каждой платформы. Откат после ошибки копирования на уровне операционной системы она не проверяет.

## Фабрика реального провайдера

`nitro-api-factory-probe` представляет собой отдельный исполняемый файл, который использует только публичный заголовок жизненного цикла и системный загрузчик. Он загружает провайдер по точному абсолютному пути, находит `CreateInterface`, запрашивает `NITRO_FRAME_LIFECYCLE_001`, создает две подписки с различными ненулевыми числовыми ID и повторно удаляет обе до уничтожения наблюдателей и выгрузки провайдера. Отсутствие провайдера, фабрики или интерфейса и некорректные ID завершают проверку ошибкой с указанием этапа. Проверка не инициализирует интеграцию NitroApi с движком.

`verify-nitro-api-factory` собирает проверочную программу и реальную динамическую библиотеку `nitro_api`. Цель подготавливает `<binaryDir>/nextclient/nitro_api/factory-probe/<config>/`, копирует провайдер и его зависимости времени выполнения, сверяет SHA-256 копий, записывает `manifest.sha256` и запускает проверочную программу с подготовленным провайдером.

В Windows фикстура предоставляет `tier0.dll`; профилирование добавляет согласованную библиотеку `TracyClient`. В Linux подготавливаются библиотеки SDK `tier0` и `vstdlib`, а `LD_LIBRARY_PATH` задается до запуска проверочной программы.

Обе проверочные цели вызываются явно и не входят в зависимости обычной сборки и установки. `BUILD_ALL` не устанавливает проверочную программу.

Цель доступна при выключенных тестах, поэтому поставляемую конфигурацию можно проверить напрямую:

```powershell
cmake --preset ninja
cmake --build --preset ninja-release --target verify-nitro-api-factory
cmake --preset ninja-profiler
cmake --build --preset ninja-profiler-release --target verify-nitro-api-factory
```

Обычная Windows-сборка проверочной программы находится в `out/bin/Release/nitro-api-factory-probe.exe`; сборка с профилированием находится в `build/ninja-profiler/out/bin/Release/nitro-api-factory-probe.exe`. Явный запуск с обычным подготовленным провайдером:

```powershell
$prepared = (Resolve-Path 'build/ninja/nextclient/nitro_api/factory-probe/Release').Path
& 'out/bin/Release/nitro-api-factory-probe.exe' (Join-Path $prepared 'nitro_api2.dll')
```

Регистрация и выполнение проверок в Linux:

```bash
cmake --preset linux -DNEXTCLIENT_BUILD_TESTS=ON
cmake --build --preset linux-release --target verify-nitro-api-factory
ctest --test-dir build/linux -C Release -R '^(installation-preflight|nitro-api-shipping-factory.*)$' --output-on-failure
```

Провайдер Linux сохраняет имя `nitro_api2.dll`. Для прямого запуска проверочной программы в Linux передайте абсолютный путь провайдера и добавьте подготовленный каталог в `LD_LIBRARY_PATH` до запуска процесса. В Windows используется переданный путь с широкими символами, `LoadLibraryExW` и `LOAD_WITH_ALTERED_SEARCH_PATH`. Это позволяет находить зависимости рядом с провайдером без подмены каталога игры. Общий загрузчик `nitro_utils` иначе обрабатывает пути и поиск зависимостей; данная проверка использует локальный загрузчик, чтобы проверить точно выбранный файл.

При включенных тестах CTest регистрирует успешный сценарий `nitro-api-shipping-factory` и отрицательный сценарий `nitro-api-shipping-factory-missing-provider`. Отрицательная проверка требует кода ошибки и сообщения об отказе на этапе загрузки. В этой конфигурации `nitro_api` остается реальной DLL; статическая тестовая библиотека `engine_mini` ее не подменяет. Проверка фабрики подтверждает регистрацию интерфейса и ABI подписок. Правила жизненного цикла определены у [владельца NitroApi](../../nextclient/nitro_api/AGENTS.md#frame-lifecycle) и [владельца мониторинга](../../nextclient/engine_mini/src/performance/AGENTS.md). Порядок вызова хуков в работающем движке, инициализация движка и завершение игры требуют отдельного наблюдения во время работы.

## Соответствие подготовленных и установленных файлов

Соберите затронутых поставщиков интерфейсов и всех потребителей измененного интерфейса из одного снимка исходников для одной платформы, пресета, конфигурации и настройки профилирования. Для мониторинга набор включает NitroApi, движок, клиент, GameUI и затронутых потребителей в launcher. `ScenePreview002` требует согласованных сборок движка и GameUI. Поставляемую DLL движка выбирайте из конфигурации с `NEXTCLIENT_BUILD_TESTS=OFF`. При включенном профилировании включите в набор согласованную библиотеку Tracy.

Перед установкой запишите сведения об исходниках и манифест с абсолютными путями подготовленных файлов, их размером и SHA-256 для полного затронутого набора модулей и ресурсов. После копирования сверьте хеш каждого установленного файла с манифестом. Сборка, проверка фабрики, установка и наблюдения в игре дают отдельные результаты. Используйте уже полученные результаты для того же снимка исходников и конфигурации. Проверки отдельных функций описаны для [мониторинга](performance-monitor.ru.md), [сцен редактора материалов](material-editor-scene.ru.md) и [рендеринга Studio](studio-rendering.ru.md).
