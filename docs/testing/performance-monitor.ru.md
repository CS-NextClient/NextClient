# Проверки мониторинга в игре

[Английская версия](performance-monitor.md) | [Использование](../performance-monitor.ru.md)

Эти проверки выполняет разработчик в игре. Для каждого сравнения сохраните ревизию, платформу, драйвер, используемый рендерер, `cl_perf`, `cl_perf_gpu`, `cl_perf_scale`, ограничение FPS, VSync, разрядность таймера GPU, состояние Tracy и вывод `perf_dump`. В одинаковой сцене сравните выключенный мониторинг, измерение CPU, измерение GPU и подключенную диагностическую запись.

## Жизненный цикл кадра и захват

| Сценарий | Ожидаемое наблюдение |
|---|---|
| Прерывание Host-кадра | Отключиться или переподключиться после вызванного сервером `Host_EndGame`, затем выполнить `perf_dump`. Измерения Studio/Radar и Host продолжаются. Прерывание во время захвата отбрасывает открытые измерения CPU/GPU и повторяет захват на следующем полном принятом кадре Host, без публикации неполных времен. Повторить с `cl_perf 0`, панелью батчинга (статистики пакетной отрисовки) и подключенным диагностическим просмотрщиком. Установить согласованные `next_engine_mini.dll` и `nitro_api2.dll` с интерфейсом `NITRO_FRAME_LIFECYCLE_001`. |
| Хронологический порядок кадров | Получить несколько выходных кадров внутри одного Host: каждый вывод кадра занимает отдельную позицию, Host и его части CPU показываются один раз у последнего выходного кадра. Host без выходного кадра получает собственную позицию; у самостоятельного выходного кадра отсутствует значение Host. Проверить одинаковые хронологические позиции на сгруппированных и отдельных графиках. Еще не полученные и отсутствующие данные GPU оставляют пустой позицию своего кадра; поздний результат заполняет исходную позицию без переноса в последний кадр. |
| Повторные ответы GPU | Проверить сопоставление результата по идентификаторам вывода кадра, Host и контекста. Проверить устаревание результатов, сброс и перезапись кольцевого буфера. Повторные идентификаторы сохраняют выбор первого совпадения и не изменяют перезаписанные или устаревшие записи. |
| Замер CPU по запросу | При cl_perf 0 и уровнях батчинга 0/1/2 команда perf_dump измеряет ровно следующий полный принятый кадр Host и автоматически выводит результат. Отклоненные и вложенные вызовы не завершают сбор. Настройки сохраняются; при выключенном мониторинге GPU-запросы не создаются. Повторный запрос не перезапускает сбор. Сброс, смена карты и выход отменяют его. Средние значения в сохраненном дампе рассчитываются по одному кадру. Текущая таблица батчинга продолжает обновляться независимо от дампа. Сравнить одну сцену между запросами и во время сбора. |
| Замена контекста | Запросы старого контекста не удаляются и не завершаются в новом. Изменение размера с тем же контекстом сохраняет запросы. |
| Обычный и контролируемый разработчиком фатальный выход | Источники данных останавливаются до уничтожения получателей. Рабочие потоки завершаются. Очистка не ожидает GPU или подключения просмотрщика. |

## Панель и история измерений

| Сценарий | Ожидаемое наблюдение |
|---|---|
| Инструменты разработчика | Задать developer 0/1 и изменить его значение при открытом меню. Проверить индикатор и четыре кнопки в левом верхнем углу обычного меню, меню с CEF и меню паузы. Переключить все режимы, изменить cvar через консоль и проверить соответствие подписей текущим значениям. Повторно загрузить каждую поставляемую тему, включая Source. Обычные, подсвеченные, нажатые и отключенные кнопки должны оставаться читаемыми на непрозрачном фоне. Во время загрузки и в редакторе материалов панель скрыта, после возвращения в меню она появляется. |
| Группы длительностей | Проверить наложенные столбцы Swap Interval и Host Frame на CPU, Render на GPU и составные столбцы измеренных частей. На CPU части Studio/Radar/Swap расположены снизу вверх, на GPU Studio/Radar. Каждый физический пиксель содержит одну позицию кадра в хронологическом порядке; CPU/GPU используют общий порядок позиций и шкалу длительности. Соседние кадры с разными длительностями сохраняют отдельные столбцы. Части относятся к тому же Host или выходному кадру, что родительский замер. CPU/GPU используют заполненные столбцы с горизонтальными верхними границами на высоте длительности собственного кадра. Отсутствующие значения оставляют пустыми соответствующие позиции. Ось, сетка и фон совпадают с полной полосой кадров. Части используют общие горизонтальные границы внутри столбца своего кадра при дробном масштабе и остаются внутри собственного родителя при изменении соседних значений или доступности частей. p99 таблиц длительности появляется после 100 корректных измерений каждой серии внутри текущего окна из N кадров. Вложенные запросы радара учитываются один раз в Radar и сохраняются в подробной диагностике. |
| Заполнение истории | После perf_reset новые позиции кадров CPU/GPU появляются справа и сдвигают предыдущие влево. Режимы 1/2/3 показывают History с подписью last N frames. N определяется физической шириной поля графика длительностей этой панели; числовой режим 1 использует собственную более узкую панель. Таблицы и графики используют одни и те же последние N позиций. Во время заполнения истории учитываются доступные корректные измерения на этих позициях. Менять масштаб и разрешение, проверяя N и соответствующие таблицы. При низком FPS сохраненные N позиций могут охватывать больше десяти секунд. Сетевые окна заполняются независимо при поступлении пакетов или входящих порядковых номеров. |
| Статистика окна кадров | Сравнить avg/p99/max и Monitor CPU с корректными измеренными значениями текущих N позиций. Отсутствующие, еще не полученные и неактивные значения не учитываются. Пиковое значение за пределами N не влияет на таблицы и шкалы графиков. p99 недоступен при 99 корректных значениях и доступен при 100 внутри текущего окна независимо от более старых измерений. Менять ширину, сужая и расширяя N, и проверять выбранные значения. История длительностей панели при низком FPS определяется числом записей; статистика истории perf_dump и FPS дампа используют отдельное десятисекундное диагностическое окно. |
| Прозрачность подложки | Менять cl_perf_background_alpha между 0, 0.2 и 1 в режимах 1/2/3, с отдельными блоками батчинга, сети и диагностики карты, затем с их сочетаниями. Общая подложка и фон графиков меняются сразу; текст, серии и акценты заголовков сохраняют свои цвета. |
| Общее оформление | Проверить режимы 1/2/3, уровни батчинга 1/2, отдельные блоки сети и диагностики карты, затем их совместное отображение. Заголовки секций используют одинаковый акцент и фон, таблицы используют общий фон заголовков и выравнивание столбцов. Разделители итоговых строк остаются видимыми. Цвета серий и индикаторов заполнения сохраняют смысл. Числовой режим показывает вложенность CPU/GPU и столбцы avg/p99/max. Проверить короткие окна и разные масштабы без отсечения обязательных сетевых строк. |
| Главное меню и `hud_draw 0` | Панель рисуется перед выводом кадра в главное окно независимо от HUD. |
| Ограничение FPS и VSync | Проверить FPS в заголовке за последние 0,5 секунды с обновлением каждые 250 мс; таблицы длительности используют текущее окно из N кадров, а FPS дампа использует отдельную десятисекундную диагностическую историю. Заголовки батчинга различают суммы счетчиков и средние времена; Calls total показывает сумму вызовов за окно. Интервалы кадра включают ожидание. Swap CPU показывает длительность вызова обмена буферов без утверждения о причине задержки. |
| Размер окна | При 1600x1200 значение `cl_perf_scale 1` использует выбранную базу. Текст и поля графиков соответствуют масштабу панели; столбцы кадров и пакетов сохраняют ширину один физический пиксель, N соответствует ширине каждого графика. Панель остается внутри окна. |
| Пиксельная сетка столбцов | В установленной игре визуально проверить столбцы CPU/GPU и сети при дробных масштабах. Каждый столбец занимает один физический пиксель; N равно ширине графика. График шириной 423 пикселя содержит 423 позиции. Соседние заполненные позиции соприкасаются, незаполненные позиции и отсутствующие значения оставляют пустые места. Ось и подписи делений расположены у левого края; фон и сетка охватывают всю ширину графика. Таблицы используют те же окна кадров или пакетов, что графики. Сравнить маркеры loss/choke с сеткой пакетов. Сравнить соседние кадры CPU/GPU разной длительности и проверить высоту каждого столбца по длительности его кадра. |

## Studio и радар

| Сценарий | Ожидаемое наблюдение |
|---|---|
| Независимый батчинг и кеш панели | При cl_perf 0 включить уровни батчинга 1/2, отдельно и вместе с сетью и диагностикой карты. Уровень 1 обновляет счетчики без CPU-замеров; уровень 2 непрерывно измеряет CPU без дампа. При cl_perf 0 GPU-запросы не создаются; основные графики скрыты. Проверить переключения, узкие и низкие окна, масштаб и новый дамп CPU. Основные графики используют кеш команд 250 мс, а таблица батчинга обновляется после каждого завершенного кадра. Изменение ревизии сети пересоздает только сетевые команды, сохраняя команды CPU/GPU и диагностики карты. Проверить одновременное обновление сети и батчинга и переходы пустого/полного окна без повреждения последующих индексов текста. После временной ошибки подготовки символа выполняется повторная попытка. Смена атласа или контекста сбрасывает кеш геометрии. Группировка по странице текстуры сохраняет отсечение, порядок и состояние вызывающего кода. Сравнить время CPU для одной нагрузки в отдельном GL-контексте при этих настройках. |
| Штатный и шейдерный Studio | Счетчики отправки соответствуют `r_studio_shader`; доступность компиляции и линковки, интервалы CPU и GPU показаны отдельно. |
| Уровни батчинга и затраты CPU | Уровень 1 показывает объединение и экономию вызовов без подробных CPU-замеров. Оба уровня хранят последние восемь завершённых принятых кадров Host, включая пустые. Уровень 2 обновляет пять категорий CPU без perf_dump на каждом кадре, в постоянном порядке названий операций CPU, со временем ms/frame, us/call и числом вызовов за окно. Позиции строк сохраняются при изменении времени и отсутствии замеров; выделение и компактная строка Top GL cost указывают фактическую наиболее затратную категорию. Отклонённые вызовы и кадры со сменой уровня исключаются; смена только cl_perf внутри кадра сохраняет счетчики первого уровня. Проверяются смена уровня, отсутствие измерений, узкие окна и возврат штатного сетевого графика. Время сохранения, восстановления и обычной смены привязок учитывается раздельно. Повторные привязки, исключенные благодаря кешу, не увеличивают счетчик вызовов. Счетчики и причины доступны в дампе. Проверяются вложенность фаз сохранения и восстановления, пять прямых дочерних этапов Studio, общий итог Other Studio и одна строка Top detail без двойного учета родителя и дочернего этапа. |
| Скрытый радар, обычный режим и полная карта | Скрытый радар неактивен. Видимые режимы сохраняют маркеры, подписи, отсечение и порядок рисования. |
| Подготовка слоев и смена карты | Время захвата данных в главном потоке учитывается отдельно от времени фонового анализа. Отмененные задачи и старые результаты GPU не заполняют текущие строки. |
| Передача данных Studio и временная память | Проверить модели с малым числом костей и со 128 костями, авторские материалы, батчи со встроенными и авторскими материалами и смену GL-контекста. После каждого батча проверить исходные текстурные привязки. Загрузка текстур, отправка и сброс очереди сохраняют правильные позы и порядок мешей. Обычные отрисовки загружают только объявленные кости модели; материалы с программами, отличными от `studio_legacy`, сохраняют полную передачу позы. |
| Подготовка Studio на CPU | Проверить обычный проход после glow shell, замену имени и заголовка модели, очистку геометрии и доступ редактора к модели, для которой подготовка геометрии завершилась ошибкой. Повторить один и тот же сегмент записанного демо по три раза на каждой сборке с одинаковыми настройками. Время кадров учитывать отдельно от однокадрового захвата `perf_dump`, включающего затраты сбора. |

## Сетевая статистика

| Сценарий | Ожидаемое наблюдение |
|---|---|
| Дополнительные блоки | Включить все мониторинги, включая режим 2 карты с 20 свойствами объекта и режим 2 батчинга, при 1600×1200 и дробном масштабе. Проверить режимы 0/1/2/3: каждый включенный мониторинг сохраняет отдельный фон и видимый зазор. Порядок: производительность, сеть, батчинг, диагностика карты, от правого верхнего угла вниз и далее в колонки слева без возврата в предыдущую колонку. В высоком окне панели остаются отдельными в одной колонке. Доступность, ширина и число позиций сетевого окна не зависят от режима производительности. Сетевые графики задержки и размеров пакетов остаются видимыми, каждый пакет занимает один физический пиксель. В режиме 3 сохраняются все восемь серий производительности. Изменить число пакетов, переместить объект и обновить счетчики батчинга: другие строки не перестраиваются, последующие блоки не повреждаются. Изменить размер окна и масштаб, проверить размещение колонок и штатный сетевой график в узком окне. |
| Штатный net_graph | Задать net_graph 3, включить cl_perf_net 1, выключить его и проверить возврат исходного отображения с сохранением настройки. Повторить при уменьшении окна и изменении net_graph во время работы блока. |
| Окна сетевых пакетов | Сравнить активную игру, ожидание данных, отключение/переподключение и просмотр демо. Размеры In/Out используют независимые окна последних N позиций пакетов; задержка и loss/choke используют N входящих порядковых номеров. Заголовок показывает last N packets, где N соответствует физической ширине графика. Новые записи появляются справа; без пакетов позиции сохраняются. Проверить пустые, частично заполненные и полные окна, серии пакетов одного направления и переполнение порядкового номера. Менять разрешение и масштаб панели, проверяя соответствие заголовка и avg/median/max текущему N. Расширение окна возвращает доступную ранее собранную историю. Нижняя строка самостоятельной панели показывает число доступных позиций In/Out в текущем окне. |
| Сетевые значения и пробелы | Сравнить Packet size (B) с учтенным движком размером пакетов, а сводные KiB/s и pps с выборками скорости за 100 мс. Задержка измеряется в миллисекундах. Таблицы avg/median/max описывают корректные значения текущих окон из N позиций пакетов. Каждый столбец содержит один замер и рисуется полупрозрачным заполнением; avg выводится в таблице. Подтвержденные состояния loss/choke обозначены отдельными маркерами порядковых номеров; сводные проценты рассчитываются по периодическим выборкам. Пропустить более 32 записей потока или 64 входящих кадров между наблюдениями и проверить пробелы на перезаписанных позициях без подстановки нулевого замера или маркера loss/choke. |

## Диагностика карты

| Сценарий | Ожидаемое наблюдение |
|---|---|
| Диагностика карты | Сравнить wpoly и стандартный epoly с r_speeds, затем шейдерный epoly с фактическими отправками. Счетчики обновляются для каждого вида и при r_speeds 0, без glFinish. Проверить число брашей на карте и в PVS, координаты, углы, точку взгляда и имя объекта. |
| Доступ к локальной карте | Задать cl_perf_map 2 до запуска локальной карты. После активации соединения loopback проверить свойства и обводку, в том числе при maxplayers 32. Подключиться к внешнему серверу или запустить демо: остается режим 1, свойства отсутствуют в панели, выводе по E и perf_dump, обводки нет. Запустить другую локальную карту без изменения cvar: возвращается режим 2. |
| Позиция объекта и подсказка E | В локальном cl_perf_map 2 сравнить Object origin с текущей позицией сущности, а Look с точкой попадания в перемещенный и повернутый браш. Переместить сущность, сменить объект и убрать взгляд с объекта: отдельная строка позиции обновляется сразу, при отсутствии объекта показывает прочерк. Для worldspawn выводится 0 0 0. Проверить постоянную подсказку E: dump to console в режимах 1/2, в том числе при переполнении списка свойств. Вывод по E и perf_dump содержит Object origin только в режиме 2. |
| Свойства объекта | На локальной карте в cl_perf_map 2 проверить текущие поля и bsp. свойства именованного браша. Сравнить полный perf_dump и число показанных свойств. Проверить явную метку bounds для Studio-модели и спрайта с масштабом. |

Проверки диагностики карты: включить `cl_perf_map 1` и `2` независимо от `cl_perf`. Сравнить wpoly/epoly с `r_speeds 1`; в PVS учитывать только брашевые модели без мира. В режиме 1 проверить, что координаты Look доступны, а строка Object, имя и свойства объекта отсутствуют в панели, выводе по E и perf_dump как при попадании, так и без него. В локальном режиме 2 проверить появление данных объекта. Проверить именованный вращающийся несолидный браш, объект за стеной, пустое небо, попадание в границы Studio-модели, меньшее окно наблюдения, масштабирование области вывода, `r_norefresh`, отключение, смену карты и `perf_reset`. В режиме 2 сравнить полный список полей объекта из `perf_dump` с обрезанными строками панели и исходными свойствами `bsp.`. Эти сценарии проверяет разработчик в установленной игре.

Проверка управления диагностикой карты: нажать и удерживать E при cl_perf_map 0/1/2. Во время игры уровни 1/2 выводят один снимок на нажатие с сохранением исходного действия клавиши. Режим 2 включает полный список свойств. Ввод в консоли, чате или меню не должен печатать снимки. В режиме 2 проверить повернутый браш, выбранный полигон мира, границы Studio-модели и спрайта, а также меньшее окно наблюдения. Ближние стены должны перекрывать скрытые ребра обводки. Проверить смену объекта, отключение, perf_reset и r_norefresh. Автоматические тесты проверяют скопированные координаты обводки и формат полного дампа. Тесты в отдельном GL-контексте проверяют отсутствие отметки в центре прицела, матрицы и буфер сцены, оба направления диапазона глубины, отсутствие записи глубины и сохранение состояния GL.

## Запись Tracy

| Сценарий | Ожидаемое наблюдение |
|---|---|
| Изменения подключения Tracy | Встроенный сбор и `perf_reset` работают независимо. При отключенных панелях все доступные CPU-этапы и существующие GPU-этапы передаются в Tracy. Графики рендеринга и батчинга публикуются один раз на принятый Host перед его маркером, сбрасываются по кадрам и не сохраняют значения кадров без подключения или отфильтрованных вызовов. График пропусков CPU отражает реальное переполнение стека; диагностические графики пропусков и устаревших результатов GPU сохраняют накопительные значения. При сборе только счетчиков Tracy встроенные таймеры монитора не вызываются. Полные клиентские колбэки моделей и игроков включают viewmodel и вызовы только для подготовки; подготовка родителя follow и разбор серверных сообщений имеют отдельные области. |
| Исходный код в Tracy | Проверьте метаданные областей CPU и GPU в новой записи. Прямые замеры и обёртки Studio/радара указывают файл, функцию и строку вызова; перехваты штатного движка указывают место регистрации в интеграции. Два места вызова одного этапа различаются, повторные вызовы используют стабильные метаданные после сброса и переподключения. Движок и клиент должны использовать `PerformanceMonitor001`. |


Перед наблюдением в игре выполните [проверки установки и реальной фабрики](installation-and-factory.ru.md) для подготовленного набора провайдеров и потребителей. Правила жизненного цикла и отложенного отключения определены у [владельца NitroApi](../../nextclient/nitro_api/AGENTS.md#frame-lifecycle) и [владельца мониторинга](../../nextclient/engine_mini/src/performance/AGENTS.md).

## Покрытие автоматических тестов

Интерфейс `NITRO_FRAME_LIFECYCLE_001` предоставляет операции `Subscribe(observer)` и `Unsubscribe(id)` в потоке Host. Каждая явная регистрация получает собственный монотонно возрастающий ненулевой ID, в том числе при повторной передаче одного указателя наблюдателя. Нулевой указатель возвращает нулевой ID. Подписчик удаляет свой ID до уничтожения наблюдателя. При завершении NitroApi все регистрации теряют силу до выгрузки модулей; их ID не используются повторно. Каждый вызов Host сохраняет снимок ID. Уведомления о входе и принятом кадре следуют порядку регистрации. Уведомления о выходе идут в обратном порядке после обычной цепочки подписчиков. Перед каждым колбэком проверяется действительность ID. Новая регистрация участвует в следующих вызовах, включая вложенный вызов, начатый после регистрации. Если колбэк входа сообщает о принятом кадре, уведомление получают только наблюдатели, чей вход уже начался. Следующие наблюдатели получают его один раз после начала своего входа.

Тесты `nitro_api-tests` проверяют независимые регистрации, отклоненные и повторные результаты фильтра, порядок относительно обычных подписчиков, самоотключение и уничтожение другого получателя на всех трех границах, очистку из колбэков, повторные указатели, устаревшие ID, добавление из колбэка, повторную регистрацию с вложенным вызовом и повторный вход в принятие кадра из колбэка входа. Проверка нелокального прерывания кадра (nonlocal abort) сохраняет переход средствами x86, соответствующий поведению движка, и проверяет границы следующего Host. Тесты `engine_mini-tests` используют владельца подписки монитора из интеграции: завершение работы внутри вложенного Host сохраняет ID до соответствующего внешнего выхода и закрытия трассировки; вне Host удаляется только собственный ID; повторная привязка удаляет прежний ID до новой регистрации. Уничтожение владельца подписки удаляет только собственный ID и не завершает монитор. Завершение монитора остается окончательным. Повторная привязка проверяет владение регистрацией.

Автоматические тесты проверяют метаданные CPU при отправке области в Tracy, разные места вызова, стабильность дескрипторов, передачу места замера CPU/GPU через мониторинг и обе области радара. Тесты геометрии команд панели проверяют выровненную вправо пиксельную сетку без зазоров у столбцов и маркеров производительности и сети, горизонтальные верхние границы CPU/GPU, сглаженные сетевые границы, пустые позиции без данных, общие горизонтальные границы частей при дробном масштабе, расположение частей внутри родительских значений кадров и заполненные столбцы.

Пакетные тесты проверяют независимые окна по ширине графика, однопиксельные столбцы пакетов, статистику текущего окна, возврат истории при расширении окна, маркеры порядковых номеров, пробелы перезаписанных записей, сохранение позиций без новых данных, исключение надежных фрагментов и старых флагов choke в потерянных порядковых номерах.

Проверки сетевого обновления сохраняют остальные секции при переходах пустого/полного окна и обновляют сеть и батчинг при одном выводе кадра без обновления содержимого CPU/GPU и диагностики карты. Тесты истории кадров проверяют отдельные значения соседних кадров, общий порядок позиций CPU/GPU, принадлежность Host и выходных кадров и поздние результаты GPU на исходных позициях кадров. Проверки сводок окна кадров охватывают общее N для графиков, таблиц и шкал, сохранение данных при низком FPS, исключенные состояния и доступность перцентилей внутри текущего окна.

Также автоматические тесты проверяют учет и историю, переходы состояния, соглашения вызова SDL и фиксированные смещения ABI, общий клиент в нескольких DLL, ограниченное резервирование запросов, реальные временные метки GL и сохранение GL-состояния панели и измеряемых отправок. Проверка панели использует тестовый поставщик шрифта с реальной загрузкой текстуры. Внешний вид шрифтов Windows проверяется в установленной игре. Отдельные GL-тесты проверяют реальные проходы радара. Пропуск из-за отсутствия возможности GPU не считается успешным измерением.

Результаты игры следует хранить отдельно от результатов сборки, тестов с подмененными компонентами и тестов в отдельном GL-контексте. Проверки в игре определяют порядок колбэков, внешний вид и затраты на сбор данных для выбранного оборудования и сцены.
