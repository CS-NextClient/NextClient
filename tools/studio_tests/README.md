# Тестовый контент для шейдерного studio-рендера

Одна карта `studio_test` и набор моделей, закрывающие то, что нельзя проверить на
стоковом контенте: ветки по флагам текстур и нагрузку на стадию подачи геометрии.

Причина существования: из 2731 модели полной инсталляции 1616 не имеют флагов вообще,
а chrome есть у 14.8%, fullbright у 0.8%. Соответствующие ветки шейдерного пути
остаются непроверенными, пока не окажется подходящего контента.

## Модели

`mdl_flags.py` не создаёт модели, а копирует заведомо валидную и переписывает только
поле флагов её текстур. Результат отличается от модели, которую игра уже рисует верно,
ровно одним свойством, поэтому расхождение на A/B нельзя списать на кривой ассет.

```bash
python tools/studio_tests/mdl_flags.py \
    "<game>/cstrike/models/player/gign/gign.mdl" \
    "<game>/cstrike/models/studio_tests"
```

Варианты: `plain`, `flatshade`, `chrome`, `chrome_flat`, `fullbright`, `masked`,
`additive`. Если у шаблона текстуры вынесены в `<имя>T.mdl`, переписывается он.

Плюс `shell`: та же модель без флагов, что и `plain`, но под своим именем. Причина не
в флагах, а в материалах: образец материала лежит рядом с `plain`
(`<имя>_plain.mat`), а материал рисует только шейдерный путь, поэтому всё, что
оценивается сравнением двух путей, обязано стоять на модели, до которой материал не
дотягивается. На `shell` стоят сущности с glow shell.

## Карта

Подписи над моделями лежат в отдельном wad, и он должен содержать текстуру на каждую
подпись, которую карта расставляет:

```bash
python tools/studio_tests/make_labels.py "<game>/cstrike/studio_test.wad" \
    plain flatshade chrome chromeflat fullbright masked additive \
    glow_rm4 add_rm5 color_rm1 shell_red shell_blue remap
```

```bash
python tools/studio_tests/make_maps.py "<game>/cstrike/maps/src" \
    --flag-models "<game>/cstrike/models/studio_tests" \
    --perf-models "<game>/cstrike_downloads/models/player" \
    --wad "<game>/valve/halflife.wad" \
    --label-wad "<game>/cstrike/studio_test.wad" \
    --remap-model-file "<game>/cstrike_downloads/models/next21_adventures/treasure.mdl"

powershell -File tools/studio_tests/build_maps.ps1
```

Две комнаты, соединённые коридором:

- **южная** (спавн) - по одному `cycler` на каждый вариант флагов в ряд, плюс три
  сущности с режимами отрисовки 4, 5 и 1 и две с glow shell. Оболочка рисуется вторым
  проходом по той же модели с принудительным хромом на каждой грани, и цвет берёт из
  `rendercolor`, поэтому их две и разного цвета: по одной нельзя отличить «цвет
  прочитан» от «цвет какой-то». Там же перед спавном лежит `armoury_entity` с АК:
  спавн на этой карте не выдаёт ничего, а присоединённое к игроку оружие это
  отдельный случай шейдерного пути, и достаётся он только ношением. С краю ряда стоит
  модель с ремап-скином (`--remap-model`, по умолчанию сундук из `next21_adventures`):
  такие модели берутся из установленного контента, их в игре десятки. Выбирается не
  первая попавшаяся, а по доле насыщенных пикселей: у сундука их девять десятых, поэтому
  замена оттенка бросается в глаза, тогда как первый образец с тремя процентами выглядел
  просто серым и не доказывал ничего. Высота берётся из бокса самой модели
  (`--remap-model-file`), потому что фиксированная подходит только моделям игроков: тот
  же первый образец висел на 129 единиц ниже своего начала координат и уходил в пол;
- **тёмная ниша** в западной части южной комнаты, закрытая коробка с одним низким
  проходом и без источников света внутри. В ровно и ярко освещённой комнате не видно
  ничего из того, что свет приносит с собой: вспышка выстрела добавляет несколько
  процентов к тому, что уже есть, и проверка сводится к гаданию. Внутри две модели,
  расставленные так, чтобы тень одной не доставала до другой, когда дойдёт очередь
  до теней;
- **северная** - сетка 12x4 из двух тяжёлых кастомных моделей по 24 штуки каждой.
  По умолчанию `YoRHa_2B` (54033 треугольника, 24 вызова отрисовки) и
  `svinorez_t_robb` (30085, 26). Две, а не много разных: повторение одной модели это
  то, на что нацелен батчинг между сущностями, а одна-единственная скрыла бы стоимость
  переключения между ними.

Коридор имеет форму буквы S. Прямой коридор оставляет комнаты взаимно видимыми при
любой ширине, и vis сваливает всё в один PVS: первый вариант скомпилировался в четыре
листа с `average leafs visible: 3`. Два поворота убирают прямую видимость. Проверяется
декодированием vis-данных из bsp: лист северной комнаты не видит лист южной и наоборот.

По той же причине vis запускается полностью, а не с `-fast`: быстрое решение это
разделение теряет. rad остаётся на `-fast`, качественный расчёт освещения коробки не
даёт ничего, а стоит минут.

## Проверка

```
map studio_test
r_studio_graph 1
r_studio_shader 1
r_studio_info
```

Строка `N calls, M by shader` и `last fallback reason` показывают итог за кадр и
последнюю подачу. Северная комната даёт числа по нагрузке; поскольку PVS раздельный,
при переходе между комнатами счётчики меняются полностью, а не суммируются.

Что именно чем нарисовано, отвечает `r_studio_dump [имя]`: он записывает следующий
кадр по строке на каждый вызов подачи в `<gamedir>/<имя>.txt` и печатает сводку по
причинам отказов. В строке видно пару «модель, заголовок» (то, на чём ломалось оружие
в руках игрока), принудительные флаги и параметры оболочки, режимы затенения и
найденные материалы с указанием, пришли ли они из серверной таблицы:

```
  17 ent=3 model=models/p_ak47.mdl hdr=p_ak47.mdl sub=244 forced=0x0000 fx=0 rm=0>0
     blend=1.00 meshes=1 shade=0 mat=1 srv=1 elight=0 -> shader
```

Файл сравнивается построчно между запусками, поэтому «стало хуже» устанавливается
диффом, а не пересмотром консоли.

Цвет перекраски задаётся полем сетевого состояния `colormap`, у любой сущности, а не
только у игрока: движок разбирает его перед отрисовкой на два байта, младший в
`r_topcolor`, старший в `r_bottomcolor`, а оттенок равен `topcolor * 360/255`. Из
плагина это ставится штатно, `set_pev(ent, pev_colormap, top | (bottom << 8))`.

Ключа для него в формате карты нет, поэтому у циклера на этой карте `colormap` равен
нулю, оттенок 0 и модель выходит красной. Проверяет она поэтому привязку, а не цвет:
обе ветки обязаны разрешить скин в одну и ту же текстуру, а до правки шейдерная
привязывала базовую. Чтобы проверить и цвет, `colormap` надо выставить, и это одна
строка в плагине.

`hdr=` это имя внутри заголовка, то есть то, под которым модель компилировали, а не
путь к файлу: у `models/player/YoRHa_2B/YoRHa_2B.mdl` там стоит `leet.mdl`. Совпадения
имён это не доказывает и не должно: пару сверяет сам код через `Mod_Extradata`, и
`-> shader` в строке уже означает, что она сошлась.

Для сравнения картинки: `pause`, затем `r_studio_ab flags` и

```bash
python tools/radar_tests/imgdiff.py flags_off.tga flags_on.tga --clusters --out flags_diff.png
```

Как выглядит хороший прогон, замерено 04.08.2026 на этой карте: `over_tol` около 0.18%,
одна группа `CONCENTRATED` на модели с подписью `fullbright` (плотность 0.56, знак +1,
среднее около +31 по яркости) и всё остальное вне плотных плиток со средним около нуля.
Единственная плотная группа при этом законна: движок флаг `fullbright` не читает, а мы
его выполняем. Любая вторая такая группа это находка.

Обратите внимание на числа: 0.181% при допуске 0.200% это формально PASS, а исторический
дефект давал 0.178%. По доле эти два случая неразличимы, и в этом весь смысл ключа.

`--clusters` здесь обязателен: общий процент расхождения не является вердиктом.
Настоящий дефект однажды дал 0.178% при допуске 0.200%, то есть формально PASS, и
отличала его не величина, а форма. Ключ раскладывает пиксели по плотно заполненным
плиткам и печатает по каждой группе знак среднего; плотная и однознаковая группа
роняет прогон независимо от процента, а размазанный по силуэтам остаток со средним
около нуля (разница точности GPU- и CPU-скиннинга) его не роняет.

Модель с `fullbright` разойдётся закономерно: движок этот флаг не читает вовсе, а
шейдерный путь его выполняет, и это намеренное расхождение.
